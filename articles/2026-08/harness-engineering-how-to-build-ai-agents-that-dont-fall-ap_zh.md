护栏工程：如何构建不会崩溃的 AI 代理

大多数人对失败代理的回应是修改提示词

然后他们更换模型

然后他们增加更大的上下文窗口

代理仍然忘记决策

它仍然使用错误的工具

它仍然跳过验证

它仍然卡在同一个循环里

问题并不总是智能本身

问题在于它周围的环境

那个环境就是护栏

而设计护栏就是护栏工程

Anthropic 首席执行官 Dario Amodei 在解释 Claude Code 如何诞生时直接说道：

“当然，你需要一个界面，你需要一个护栏来使用它们。”
我在 Substack 上发布关于 AI 代理、工作流和生产系统的实用解析，在此加入订阅。

模型只是推理引擎

模型可以建议下一个动作

它无法自行创建可靠的操作环境

护栏决定模型能看到什么、能接触什么、会话之间保留什么、什么算作证据，以及运行何时必须停止

```text
模型
推理并提议动作

护栏
选择上下文
暴露工具
存储状态
执行权限
检查结果
记录轨迹
从失败中恢复
```

提示词是这个系统中的一个组件

模型是另一个组件

产品是当所有周围组件协同工作时产生的结果

提示词工程改进指令

护栏工程改进指令执行的条件

同一个模型可以变成完全不同的代理

把同一个模型放进聊天框，它会回答问题

把它放进一个具有终端访问、测试、浏览器工具、项目记忆、隔离工作树和审查循环的仓库中，它就能交付软件

权重没有改变

改变的是护栏

OpenAI 在使用 Codex 构建以代理优先的代码库时描述了同样的转变

他们早期进展缓慢是因为环境定义不充分，而不是因为模型缺乏原始能力

回应不是告诉代理更努力地尝试

而是询问缺少什么能力，并让该能力既清晰又可执行

“环境定义不充分”

OpenAI，《护栏工程：在以代理优先的世界中利用 Codex》

这是核心思想

当代理反复失败时，停止编辑提示词中的形容词

检查模型周围的系统

生产级护栏有七项职责

1. 将请求转化为契约

在代理行动之前，将请求转换为一个有边界的对象

```text
{
 "goal": "交付该功能",
 "inputs": ["问题", "仓库", "设计"],
 "output": "可审查的拉取请求",
 "constraints": ["不更改模式", "保留公共 API"],
 "done_when": ["测试通过", "视觉检查通过", "审查通过"]
}
```

契约保护任务不被悄然重新定义

没有它，代理可能完成一个不同的工作却仍然宣布成功

2. 给代理一张地图

代理需要项目知识

它们不需要每个上下文窗口中的每份文档

使用一个小的根指南，告诉代理去哪里查找

```text
AGENTS.md
 -> 架构地图
 -> 测试地图
 -> 产品规则
 -> 安全规则
 -> 任务特定指南
```

地图保留上下文

巨大的手册消耗上下文

将详细知识放在它所管理的代码、工具或工作流附近

仅在当前任务需要时加载它

3. 在正确的环境中暴露正确的工具

工具访问不是按钮列表

它是模型与现实世界之间的接口

每个工具都需要明确的目的、可预测的输出、明确的失败状态和权限边界

```text
读取文件 默认允许
运行测试 在沙箱内允许
写入文件 在工作区内允许
访问网络 按任务范围限定
部署 需要审批
删除数据 需要审批
```

好的工具在模型有机会错误推理之前减少歧义

坏的工具迫使模型猜测发生了什么

4. 将记忆外部化为持久状态

对话不是记录系统

将决策、工件、失败和未决风险存储在上下文窗口之外

```text
{
 "task_id": "task_042",
 "current_step": "verify_ui",
 "artifacts": ["build.zip", "report.md", "screenshot.png"],
 "decisions": ["keep existing schema"],
 "failures": ["mobile overflow at 390px"],
 "pending": ["human approval"]
}
```

下一个会话应该继承工作状态，而不是对话的有损复述

这就是代理如何在上下文重置、崩溃和交接中存活下来的方式

5. 在增加自主性之前添加传感器

代理无法纠正它无法观察到的东西

测试、代码检查器、截图、日志、指标和模式验证器将模糊的质量转化为证据

```text
代码 -> 测试 + 类型检查 + 代码检查
UI -> 渲染 + 截图 + 视觉检查
研究 -> 来源检查 + 矛盾检查
数据 -> 模式 + 范围 + 新鲜度检查
```

模型创建工件

环境产生关于工件的证据

护栏决定该证据是否足以继续

6. 在模型之外执行权限

模型可以推荐一个动作

护栏必须授权它

```text
模型建议 -> 策略检查 -> 工具执行
```

当动作昂贵、不可逆或涉及他人时，这种分离最为重要

不要要求同一个概率系统去制定计划、批准风险并执行副作用

7. 记录轨迹并在本地恢复

每次运行都应留下可读的痕迹

```text
请求
选中的上下文
工具调用
状态更改
验证结果
重试
成本
最终工件
回滚点
```

没有轨迹，失败变成谜团

有了轨迹，失败成为下一次护栏改进的输入

指令应该成为基础设施

大多数团队用散文形式保留重要规则

代理阅读它们

然后最终忽略其中一条

更强的模式是将重要规则编码两次

首先作为代理能理解的指导

然后作为代理无法绕过的机械检查

```text
指导
“UI 代码不得直接查询数据库”

检查
当 UI 导入仓库层时，代码检查失败
```

指导解释原因

检查执行边界

这会将过去的失败转化为永久的系统改进

下一个代理不需要记住该事件

护栏替它记住

循环属于护栏

长期运行的工作需要迭代

但“不断尝试直到成功”不是控制系统

一个有用的循环有证据、有界重试、预算和升级路径

```text
for (let attempt = 1; attempt <= 3; attempt += 1) {
 const artifact = await build(state)
 const evidence = await verify(artifact)

 if (evidence.pass) return artifact

 state.failures.push(evidence.gap)
 state.repair = evidence.repair
}

return requestHumanReview(state)
```

模型应该决定如何修复局部差距

护栏应该决定是否允许再次尝试

Anthropic 在长期运行代理的工作中得出了类似的结论

结构化工件在会话之间保持连续性，而独立的评估器给构建者具体的反馈，而不是让它批准自己的工作

“找到尽可能简单的解决方案，只在需要时增加复杂性”

Anthropic，《长期运行应用开发的护栏设计》

失败应该升级系统

大多数人修复当前输出

护栏工程师修复失败类别

```text
缺少上下文 -> 添加地图或检索规则
错误的工具 -> 改进工具描述或路由
糟糕的输出 -> 添加验证器或更强的契约
重复循环 -> 添加重试上限和升级
不安全的动作 -> 添加权限门
丢失决策 -> 将其存储在持久状态中
未知失败 -> 添加追踪和证据捕获
```

即时补丁修复一次运行

护栏更改改进其后的每次运行

这就是复利优势

一个好的约束框架将代理的错误转化为基础设施

分离大脑、双手与历史

当三个组件相互分离时，可靠的代理更容易被推理和理解

```text
大脑
负责推理的模型

双手
负责行动的沙箱与工具

历史
所发生事件的仅追加记录
```

如果沙箱消亡，历史依然存在

如果模型更换，工具与策略仍然可审查

如果任务恢复，新的会话可以从产物和轨迹中重建状态

Anthropic 的托管代理架构通过会话、约束框架和沙箱使这种分离变得明确

https://x.com/i/web/status/2041927687460024721

重要的不是供应商

而是架构

推理引擎不应同时充当文件系统、权限系统、内存数据库和审计日志

为每次运行提供变更凭证

当代理完成时，不要只保留最终输出

保留一份简洁的凭证，说明输出是如何产生的

```text
{
 "context_sources": ["issue", "repo_map", "design_spec"],
 "policy_version": "v12",
 "model_route": "complex_coding",
 "tools_used": ["shell", "browser", "tests"],
 "tests": { "passed": 42, "failed": 0 },
 "human_corrections": 1,
 "retries": 2,
 "cost_usd": 3.84,
 "accepted_artifact": "pr_1842",
 "rollback_point": "commit_7f3a"
}
```

这使得模型升级具有可比性

使回归问题可归因

使审计成为可能

并且防止最终答案掩盖有缺陷的过程

从最小的闭环约束框架开始

约束框架工程并不意味着在第一个任务之前就构建一个平台

从最小的可观察、可验证、可恢复的系统开始

```text
级别 0
提示 + 模型

级别 1
项目指南 + 工具

级别 2
结构化状态 + 测试 + 有界循环

级别 3
权限 + 轨迹 + 恢复 + 人工门控
```

只有当任务需要时，才向上提升复杂度

一个简短的低风险任务可能只需要一个提示和一次审查

一个六小时的编码运行，可以编辑文件、访问网络并提交拉取请求，需要一个真正的约束框架

约束框架应该小于它所控制的故障面

约束框架工程检查清单

在信任代理处理真实工作之前，请确认：

```text
[ ] 执行开始前是否已定义成功标准
[ ] 代理能否在不加载全部内容的情况下找到正确的项目知识
[ ] 每个工具是否有明确的契约和失败状态
[ ] 执行是否与生产系统隔离
[ ] 重要决策是否存储在对话之外
[ ] 每次有风险的转换是否有证据
[ ] 不可逆操作是否受审批保护
[ ] 每个循环是否有重试上限和预算
[ ] 运行中断后能否恢复
[ ] 你能否解释每次工具调用和状态变更
[ ] 失败是否会更新指南、测试、工具或策略
[ ] 最终产物能否回滚
```

如果多个答案为否，更强的模型不会使系统更可靠

只会让失败更加昂贵

真正的转变

提示工程告诉模型该做什么

上下文工程决定模型看到什么

约束框架工程构建模型在其中行动的世界

```text
提示 -> 指令
上下文 -> 工作视图
约束框架 -> 操作系统
循环 -> 局部改进
图谱 -> 协调
```

模型下个月可能就会更换

工具、测试、状态、策略和轨迹可以持续改进

这就是为什么持久的优势正在从提示中转移到围绕它的系统之中

最优秀的构建者不仅会问哪个模型最聪明

他们还会问哪种环境能让这种智能变得可靠

这就是约束框架工程
