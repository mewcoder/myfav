在优步规模下高效运行软件工厂

简介

AI工具现已融入 Uber 软件开发的每个阶段。超过 70% 的拉取请求由本地或云端的智能体（agents）完成。工程师们已构建了超过 3600 个涵盖软件开发生命周期的智能体（agent） skill，每天执行超过 3 万次agent skill操作。

在AI Engineer 2026 大会上，我们分享了对“软件工厂”的愿景，以及我们正在整个生命周期中构建的基础设施和托管智能体（Managed Agents）。随着这一愿景的推进，越来越多的会话并非由人类发起，而是由自动化托管智能体处理，它们负责代码审查、自我修复 CI 故障、通过视觉验证完成端到端 PR、分类处理待命警报、调试传入的缺陷，并处理各类需要人类审查/升级的代码维护任务。

如图1所示，从2026年2月到8月，我们所有员工（工程师与非工程师）使用的所有智能体式（agentic）产品的周活跃用户增长了7倍，每周的agentic请求量增长了9.4倍。与此同时，由于全面的优化，我们的总AI支出自4月以来已趋于相对稳定。

图 1：2026年2月至8月中旬的每周活跃用户数、Agent 请求数及成本（已跨工具去重）。

由于采用率、工作负载组合和模型升级都在持续变化，要隔离我们自身的优化收益，就必须固定一个模型，因为每次升级和模型系列的切换都会带来行为变化。我们在二月到七月间执行了这一方法：每 1,000 次模型请求的成本较峰值下降了近 34%，每次会话的成本较六月峰值下降了 52%。

本文将深入探讨我们对软件工厂的思考方式：智能体（AI Agent）会话运行的四个层级、我们用来分解开支的成本公式、如何衡量每一项，以及如何在每一层优化这些项。

本比较中的所有定价和供应商指标均基于公开信息，成本效益提升源于我们更智能地将内部 Uber 工作负载路由到标准层级定价内。虽然我们衡量到的具体成本降低是我们环境独有的，且根据您的代码库、团队规模和智能体工作流（workflows）不同，您的实际效果可能有所差异，但对实际工作进行基准测试并针对准确性和成本进行优化的方法论是普遍适用的。

优化价格 / Token

厂商设定 Token 价格，我们决定哪个模型运行哪个工作负载。在所有受管智能体层中，我们都为该工作负载选择帕累托效率最高的模型。对我们而言，帕累托效率指的是完成任务的成本、输出质量以及模型可靠性三者的最优平衡。

基准驱动的模型选择

模型选择包含四个步骤，适用于我们运行的每一个托管智能体（Managed Agent）。

基于智能体的实际工作构建基准测试。
在能够通过单一接口服务任意模型（无论是前沿模型还是开源模型）的运行框架（harness）上运行智能体。
转向帕累托最优解，并持续迭代。前沿技术每隔几周就会发生变化。

展望未来，我们将持续利用托管智能体的聚合洞察来测试和部署各种模型路由（model routing）策略，从而不断优化工作负载性能。

例如，我们使用了uReview，它为所有拉取请求处理AI代码审查。我们根据存在已知缺陷的真实拉取请求构建了其基准测试，并将难度分为简单、中等和困难。我们针对这些缺陷评估精确率、召回率和 F1 值，同时评估每次审查的成本、延迟（latency）、超时情况和噪声。如图 5 所示，切换模型在显著降低每拉取请求成本的同时提升了 F1 值。图中虚线为帕累托前沿。其下方和左侧的所有内容都已被更便宜或更优的方案所超越。

图 5：我们为uReview测试的每种配置。

利用海量真实世界的拉取请求（PR）构建于我们的大型单体仓库（monorepo）之上，我们内部同样拥有一个 Uber SWE 基准测试，它在不同的任务类型上运行前沿模型与开放权重模型。我们利用它为所有由我们的软件开发生命周期（SDLC）管理的智能体（Agent）提供模型选择的决策依据。

默认模型选择

在交互界面中，单个 Token 的成本保持固定；然而，您可以策略性地管理不同模型间的 Token 分配。两个默认设置主要控制着这种分配：初始会话模型与子 Agent（subagent）模型。

子 Agent 默认设置已被证明是最具影响力的杠杆，其重要性还在持续增长。启动子 Agent（subagents）的会话比例稳步提升，因为最新模型的能力使更高效的多智能体（multi-agent）编排成为可能。由于子 Agent 执行的是定义明确的任务，其输入通常无需前沿级推理，我们默认让其使用更弱、更具成本效益的模型，同时仍允许手动覆盖。主模型负责任务拆解（task decomposition）和评测（evaluation），而子 Agent 执行具体工作。

优化令牌 / 请求

每次轮次都会重新发送完整的对话历史、项目上下文和工具结果。任何能够减少单次请求负载的措施，在整个会话中都会产生累积效应。

所有交互式 Harness 均使用统一的封装器进行安装管理、配置、认证以及成本可视化。两种标准化的默认配置可直接降低每次请求的 Token 消耗：

即使对于拥有百万级上下文窗口（context window）的模型，自动压缩也会在 400k Token 时触发：此阈值在模型性能与缓存突发及重复输入 Token 成本之间取得了平衡。我们的测量数据显示，每个请求的全局输入 Token 数量显著降低。

提示词（Prompt）缓存策略

我们的提示词缓存（Prompt Caching）策略由提供方的提示词缓存读写经济学驱动。由于每次交互都会重新传输完整的对话历史，缓存先前的上下文可以避免重复支付全额成本，将后续读取的费用降至标准输入 Token 费率的仅 0.1 倍。然而，写入溢价各不相同：5 分钟的缓存条目成本为 1.25 倍，而 1 小时的条目成本为 2 倍。因此，选择最优的 TTL（生存时间）取决于交互轮次之间的间隔时长。可用的 TTL 选项包括 Anthropic® 提供的 5 分钟和 1 小时，以及OpenAI® 提供的 30 分钟。

图 6：两种 TTL 持续时间下 5 轮对话的对比。

由于工程师经常将交互式会话闲置超过5分钟，我们已将默认的5分钟TTL（Time To Live，生存时间）切换为1小时窗口。这些频繁的闲置间隔此前会使前缀缓存失效，从而被迫进行昂贵的全价上下文重建。相比之下，子Agent（Subagent）保持了5分钟的缓存TTL，因为它们的执行焦点仅限于单个短期任务。

通过 Shell 执行MCP工具

在 Uber，所有MCP（模型上下文协议（Model Context Protocol））交互都通过一个统一的网关进行路由。这个单一入口点涵盖了内部和第三方 SaaS MCP中超过 1,000 个MCP服务器，从而实现集中的身份验证和策略执行。

然而，标准的MCP实现会直接将所有工具 schema 加载到每个会话中，无论工程师是否会在该会话中调用它们。例如，在安装了超过 100 个工具的情况下，这种预加载会为初始 Prompt 增加大约 50K-70K Token 的模式（schema）开销，而这个开销随后会在每个上下文轮次中被重复发送。

图 7：在会话开始时，智能体已携带的内容，以及三种触达相同工具的路径。

为解决此上下文膨胀问题，我们引入了两项互补的优化机制：

CLI工具解析：通过允许模型执行 shell 命令来替代直接的MCP集成。该CLI在调用时动态解析并针对网关调用所需工具，从而在会话上下文中消除了庞大的MCP模式。我们内部MCP网关的全部 1000 多个MCP工具都以CLI命令的形式被映射出来。
工具搜索：通过允许模型搜索工具目录并按需加载所需工具，从而扩展到支持数千个工具。这种方法缓解了上下文膨胀问题，通常减少了工具定义的Token 用量（token usage），并且即使可用工具库不断扩展，也能保持高选择准确度，防止因大型工具集导致的性能下降。

代码模式

当工具直接以 shell 命令调用函数时，模型可以在单个脚本中批量执行多个操作。这种批量处理对于交互频繁的工具协议尤其有利。在标准的MCP工作流下，每个操作都需要模型单独发起一次请求、将原始响应加载到上下文窗口，并依次处理结果。例如，执行单个 SQL 查询需要提交请求、轮询状态 2 到 5 次，然后获取输出。代码模式将整个流程简化为一个自动化的Python循环，将中间的轮询过程排除在模型的活跃上下文之外。如左侧图 8 所示，模型参与了轮询循环，每次响应都会进入其上下文。而在右侧，循环在子进程中运行，只有最终的摘要结果返回给模型。

批量工作流（Bulk workflows）能放大这种效应，因为原本需要 N 次模型调用的循环，现在被一个脚本替代，节省效果叠加后超过 90%。通过为访问量最高的MCP服务器部署超过 25 个预构建的代码模式技能（code-mode skills），我们确保标准工作流默认采用最具成本效益的路径。

SaaS MCPs

管理第三方软件远比管理我们内部服务器更具挑战性。供应商设计MCP服务器时，旨在暴露其产品的全部功能，因为他们无法预判具体的客户使用场景。例如，某个工作区套件将 49 种工具捆绑在一个服务器中，其 schema 需要约 22K 个 token；而即时通讯和项目跟踪供应商则分别提供 34 和 46 种工具。加载两到三个供应商服务器，就会让 Agent 携带的 schema 开销，甚至超过了用户输入提示词之前正在编辑的文件本身。

为了解决这个问题，我们通过自己的MCP网关来路由 SaaS MCP服务器，采用与我们内部 MCP 相同的机制。我们还将所有这些 MCP 以 CLI 的形式暴露出来，供任何智能体界面（agentic surface）调用。此外，我们在代码模式插件中为每个服务器编写了专用的 Agent Skill，以封装常见的工作流。这为跨多个 SaaS 供应商实现高效的 Agentic 工作流奠定了基础。

图 9：每个 SaaS MCP服务器都暴露在我们的MCP网关之后，以确保统一、高效的访问模式。

优化请求/轮次

无上下文的智能体（Agent）失败得缓慢而非廉价，它会反复将不断膨胀的上下文窗口（Context Window）发送到搜索下一个位置。因此，提前提供更丰富的信息，依然是降低这种搜索开销最有效的单一杠杆。

上下文工程（Context Engineering）上下文工程

在 Uber 庞大的代码库与数据生态系统中——包含数亿行代码和数千张表——智能体的大部分交互时间都花在定位信息上，而非生成代码。为此，我们设计了AI Context 图（Graph）：一个统一的网络，涵盖 2400 万个节点（nodes）和 8000 万条边（edges），横跨 86 种节点类型和 117 种边（edge）类型。该图谱集成了超过 30 个内部系统的数据，包括服务、工程团队、事件日志、Pull Request、架构设计文档、部署记录、数据集以及历史表使用查询，并允许任何智能体通过自然语言进行查询。

可见性与消耗层级

为避免实施严格的固定限额，我们采用了实时支出跟踪与自动提醒机制：

状态栏实时计数器。运行时会话成本始终在终端可见。
Harness 资源池。所有交互式 Harness 共享一个通用层级，而非按工具划分预算。托管智能体（Managed Agents）则拥有独立的层级。
Slack 提醒通知。在预期支出达到 50%、80%、100% 时发送警报，让工程师有时间规划。
便捷审批流程。层级升级需要经理审批，并支持快速生效。
成本检查技能（Skill）与提示。一个提供按需成本分解和实时状态行指导的仪表盘技能。

这使得工程师能够独立评估任务投资回报率，同时控制成本激增的风险。

会话分析仪表盘

虽然状态栏突出了会话的总开销，但它缺乏对成本驱动因素或可操作的效率步骤的可见性。通用指南提供了高层次原则，但无法评估单个开发者工作流。会话分析仪表板通过直接检查会话产物来弥合这一差距。

它直接内置于运行时（runtime）中，无需任何设置或主动启用。执行成本仪表盘技能会分析用户在所有使用的运行框架（Harness）中，跨本地和远程云沙箱的所有会话轨迹（Trace）。它并非生成一个汇总指标，而是会标记出跨会话的 16 种不同反模式，并为每种模式配以财务影响说明和针对性的补救措施。其中一些类别包括：

次优模型路由：在 Opus 上执行 Sonnet 轻松即可完成的简单多轮会话。
上下文窗口膨胀：大型MCP载荷（例如 40KB 的响应）持续存在于上下文中，并在后续轮次中产生重复计费。
缓存过期效率低下：在长时间中断后恢复会话，过期的提示词缓存迫使以全价重建前缀。
提示词初始化开销：在提供任何用户输入之前，预加载 100,000 个 Token 的系统指令和工具定义。

下一步是什么？

当前正在进行中的计划包括：

扩展托管 Agent 族群：针对每个新增 Agent，我们遵循统一的技术路线图：确立目标成果指标、构建评测基准，并选定帕累托最优模型。此系统性方法旨在将软件开发生命周期的每个阶段提升至更高的工厂成熟度模型层级。
动态模型路由：我们正在扩展涵盖多样化编程语言、代码仓库与 Agent 模态的评测基准覆盖范围。鉴于模型能力差异显著，有效的模型路由高度依赖于全面的评测。

持续技能优化：我们正在开发一种自动化方法，用于记录 Agent Skill 执行过程中的痛点，并从收集的 Trace 中自动生成技能更新。
结论

管理和抑制不断上涨的AI编码成本也是一个可解决的工程挑战。通过消除浪费的、零价值的 Token 消耗，而非仅仅依赖更低的单位价格或降级工具，我们将使用量扩大了 7 倍，同时降低了所有指标的单位成本，并提升/保持了输出质量。

核心战略转变是从交互式开发者工作流转向全托管智能体。将软件开发生命周期负载迁移至托管环境，能实现对模型路由、执行 Harness 和运营开销的完全掌控。优化一支由专业托管智能体组成的集群——每个智能体均配备专属评测基准和帕累托最优模型——在成本效益与可扩展性上，本质上优于对数千名工程师各自的终端会话进行逐一优化。
