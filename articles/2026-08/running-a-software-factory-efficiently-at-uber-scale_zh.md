# 在Uber规模下高效运行软件工厂

文章作者：@udaykiran

## 引言

AI工具现已嵌入Uber软件开发的每个阶段。超过70%的拉取请求归因于本地或云端代理。工程师们已在软件开发生命周期中构建了超过3,600项代理技能，每天执行超过30,000次代理技能。

在AI Engineer 2026大会上，我们分享了软件工厂的愿景，以及我们正在整个生命周期中构建的组件和托管代理。随着这一愿景的推进，越来越多的会话并非由人类发起，而是由自动化托管代理处理代码审查、自愈CI失败、完成带视觉验证的端到端PR、分类值班警报、调试传入的缺陷，并在人工审查/升级下处理各种代码维护任务。

如图1所示，从2026年2月到8月，我们所有员工（工程师与非工程师）在所有代理产品中的每周活跃用户增长了7倍，每周代理请求增长了9.4倍。与此同时，由于全面的优化，我们的AI总支出自4月以来相对稳定。

图1：2026年2月至8月中旬的每周活跃用户、代理请求和成本，用户跨工具去重。

由于采用率、工作负载组合和模型升级都在不断变化，要分离我们自身的优化收益，就需要固定一个模型，因为每次升级和模型系列都会导致行为变化。我们从2月到7月这样做了：每1,000次模型请求的成本较峰值下降了近34%，每次会话成本较6月峰值下降了52%。

图2：模型保持不变时的成本优化影响。*每次会话成本数据从5月底开始。

这篇博客将介绍我们对软件工厂的思考方式：代理会话运行的四个层、我们用于分解支出的成本方程、如何衡量每一项，以及如何在每一层优化这些项。

本比较中的所有定价和供应商指标均基于公开可用信息，成本效率的提升源于我们在标准分层定价内更智能地路由内部Uber工作负载。虽然我们衡量的具体成本降低是我们环境所特有的，你的结果可能因代码库、团队规模和代理工作流而异，但以真实工作为基准并针对准确性和成本进行优化的方法论是普遍适用的。

### 成本方程

在上述任何层中，我们都可以将代理会话的成本分解为以下各项，这些项可以独立衡量和优化。

图4：总支出，分解为六个相乘的项。

前两项代表采用与参与度，我们希望在整个用户群中持续增长，无论用户是交互式使用，还是代理代表他们处理任务。中间三项提供了优化机会：代理在工程师实际提出的请求之上，为自身利益所做的工作。这是我们大部分精力所在。这包括帮助代理更快规划、减少不必要的轮次或错误、优化输入令牌等机制。

### 优化杠杆

在以下部分，我们详细介绍了用于优化成本方程各部分的关键杠杆。其中一些杠杆影响成本方程中的一行或多行。

### 优化价格/令牌

供应商设定令牌价格。我们选择哪个模型运行哪个工作负载。在我们所有托管代理的层中，我们为该工作负载选择最帕累托高效的模型。对我们而言，帕累托高效意味着成本/完成任务、输出质量和模型可靠性。

#### 基准驱动的模型选择

模型选择分四步进行，对我们运行的每个托管代理都是相同的。

- 从代理的真实工作构建基准。
- 在支持任何模型（前沿或开放权重）的测试平台上运行代理，统一接口。
- 转向任何帕累托最优的模型，并持续迁移。前沿每隔几周就会变化。

展望未来，我们通过利用托管代理的聚合洞察，不断优化工作负载性能，以测试和部署各种模型路由策略。

例如，我们使用uReview，它处理所有拉取请求的AI代码审查。我们从包含已知缺陷的真实拉取请求构建了其基准，并将它们分为简单、中等和困难三个等级。我们针对这些缺陷计算精确率、召回率和F1分数，以及每次审查的成本、延迟、超时和噪音。如图5所示，切换模型提高了我们的F1分数，同时大幅降低了每次PR的成本。在图中，虚线是帕累托前沿。位于其下方和左侧的所有配置都被更便宜或更好的配置所击败。

图5：我们为uReview测试的每种配置。

利用我们大型单体仓库中的数千个真实PR，我们内部还拥有一个Uber SWE基准，该基准在不同任务类型上运行前沿和开放权重模型。我们用它来为所有SDLC托管代理的模型选择提供依据。

#### 默认模型选择

在交互式界面中，令牌单位成本保持不变；但是，你可以战略性地管理跨模型的令牌分配。两个默认设置主要控制这种分配：初始会话模型和子代理模型。

子代理默认设置已被证明是最有影响力的杠杆，其重要性持续增长。随着最新模型能力实现更有效的多代理编排，启动子代理的会话比例稳步上升。由于子代理执行具有指定输入的定义明确的任务，这些任务通常不需要前沿级推理，我们将它们默认设置为较弱但更具成本效益的模型，同时仍允许手动覆盖。主模型处理任务分解和评估，而子代理执行工作。

### 优化令牌/请求

每一轮都会重新发送完整的对话历史、项目上下文和工具结果。任何减少每次请求负载的措施都会在会话中产生复合效应。

#### 默认设置

所有交互式测试平台都使用统一的包装器进行安装管理、配置、身份验证和成本可见性。两个标准化的默认配置直接减少了每次请求的令牌消耗：

- 即使对于1M上下文窗口模型，自动压缩也会在400k令牌时触发：该阈值在模型性能与缓存突发和重复输入令牌成本之间取得平衡。我们的测量显示，整个集群中每次请求的输入令牌显著减少。
- 推理努力默认设置为中等：输出令牌（包括内部推理令牌）在主模型上按输入令牌费率的倍数计费；此策略调整直接减少了最高成本令牌类别的支出。对于一大类任务，中等推理在成本与质量之间取得了良好的平衡。

### 提示缓存策略

我们的提示缓存策略由提供商提示缓存读取和写入的经济性驱动。由于每一轮都会重新传输完整的对话历史，缓存先前上下文可以避免反复支付全价成本，将后续读取降低到标准输入令牌费率的 0.1 倍。然而，写入溢价各不相同：5 分钟缓存条目成本为 1.25 倍，而 1 小时条目成本为 2 倍。因此，选择最佳 TTL（生存时间）取决于轮次之间的间隔时长。可用的 TTL 选项包括 Anthropic® 提供的 5 分钟和 1 小时，以及 OpenAI® 提供的 30 分钟。

图 6：两种 TTL 时长下 5 轮对话的对比。

由于工程师经常让交互式会话空闲超过 5 分钟，我们将默认的 5 分钟 TTL 切换为 1 小时窗口。这些频繁的空闲间隔此前会使前缀缓存失效，迫使进行昂贵的全价上下文重建。相比之下，子代理保留 5 分钟缓存 TTL，因为它们的执行重点仅限于单个、短期的任务。

通过 Shell 执行 MCP 工具

在 Uber，所有 MCP（模型上下文协议）交互都通过统一网关路由。这个单一入口涵盖内部和第三方 SaaS MCP 中的 1,000 多个 MCP 服务器，实现集中式身份验证和策略执行。

然而，标准 MCP 会将所有工具模式直接加载到每个会话中，无论工程师在该会话中是否会调用它们。例如，安装了超过 100 个工具时，这种预加载会向初始提示中添加约 50K-70K 令牌的模式开销，并在每次上下文轮转时重新发送。

图 7：在会话开始时，代理在 3 种访问相同工具的方式下已经携带的内容。

为了解决这种上下文膨胀，我们引入了两种互补的优化机制：

CLI 工具解析：通过允许模型执行 shell 命令来替代直接 MCP 集成。CLI 在调用时动态解析并调用网关上的所需工具，从而将会话上下文中的 Uber MCP 模式消除。来自我们内部 MCP 网关的所有 1K+ MCP 工具都被投影为 CLI 命令。
工具搜索：通过允许模型搜索工具目录并按需仅加载所需工具，扩展到数千个工具。这种方法缓解了上下文膨胀，通常减少工具定义的令牌使用量，并且即使可用工具库扩展，也能保持高选择准确性，防止与大型工具集相关的性能下降。

代码模式

当工具直接作为 shell 命令调用函数时，模型可以在单个脚本中批量处理多个操作。这种批处理对于“话痨”型工具协议尤其有利。在标准 MCP 工作流下，每个操作都需要单独的模型轮次来发出请求、将原始响应加载到上下文窗口中，并顺序处理结果。例如，执行单个 SQL 查询需要提交请求、轮询状态 2 到 5 次，并检索输出。代码模式将整个流程简化为自动化的 Python 循环，使中间轮询保持在模型的活跃上下文之外。如图 8 左侧所示，模型参与轮询循环，每个响应都进入其上下文。右侧，循环在子进程中运行，只有摘要返回。

图 8：同一个仓库查询，两种方式。

我们通过在同一会话中通过两条路径运行 5 个相同的 SQL 查询来衡量这一点：

前三行突出了主要发现：即使对于远低于响应大小限制的最小结果集，代码模式也能将令牌使用量减少超过 50%。这些效率并非来自绕过大型数据负载，而是源于消除不必要的开销，包括模式初始化、多轮轮询和冗余的逐步推理。

批量工作流会放大这种效果，因为原本需要 N 个模型轮次的循环变成了一个脚本，节省量复合增长超过 90%。通过为我们最常访问的 MCP 服务器部署超过 25 个预构建的代码模式技能，我们确保标准工作流默认采用最具成本效益的路径。

SaaS MCP

管理第三方软件被证明比我们的内部服务器更具挑战性。供应商设计 MCP 服务器以暴露完整的产品功能，因为他们无法预测特定客户的使用方式。例如，一个工作区套件将 49 个工具捆绑到单个服务器中，需要约 22K 令牌的模式，而消息和项目跟踪供应商分别提供 34 个和 46 个工具。加载两到三个供应商服务器会使代理在用户输入提示之前就携带比正在编辑的文件更多的模式开销。

为了解决这个问题，我们通过 MCP 网关路由 SaaS MCP 服务器，使用与内部 MCP 相同的机制。我们还将所有这些 MCP 暴露为 CLI，任何代理表面都可以调用。此外，我们在代码模式插件中为每个服务器编写了专门的技能，以封装常见工作流。这解锁了跨多个 SaaS 供应商的高效代理工作流。

图 9：每个 SaaS MCP 服务器都暴露在我们的 MCP 网关后面，以确保统一、高效的访问模式。

优化请求 / 轮次

一个没有接地（grounded）的代理会缓慢而非廉价地失败，反复发送不断扩大的上下文窗口来搜索另一个位置。预先提供更丰富的信息仍然是减少这种搜索开销的最有力杠杆。

上下文工程

在 Uber 庞大的代码库和数据生态系统中，包含数亿行代码和数千张表，代理将大部分轮次用于定位信息，而不是生成代码。为了解决这个问题，我们构建了 AI 上下文图：一个统一网络，包含 2400 万个节点和 8000 万条边，跨越 86 种节点和 117 种边类型。它整合了来自 30 多个内部系统的数据，包括服务、工程团队、事件日志、拉取请求、架构设计文档、部署、数据集和历史表使用查询，并允许任何代理用自然语言查询它。

图 10：在有无图接地的情况下，相同提示提交给相同模型的执行路径对比。

接地的代理查询了历史使用情况，识别出超过 50 位分析师使用的特定表，并在 38 秒内给出了答案。相反，未接地的代理无法看到该表；它花了 20 分钟检查服务代码，生成了 2 个子代理，遇到 3 个错误，最后错误地得出结论：该数据集不可查询。

可见性与教育

这里的杠杆是可见性和反馈循环，帮助工程师和代理更快地收敛。

状态行

我们在工具状态行中放置了一个实时成本计数器，跟踪每个工具以及每个用户所有工具的实时支出。

图 11：状态行，以及随附的会话分析器和效率指南。

可见性与支出层级

为了避免施加严格上限，我们实现了实时支出跟踪和自动提醒：

状态行实时计数器。运行中的会话成本始终在终端中可见。
工具池。所有交互式工具共享一个层级，而不是按工具预算。托管代理有单独的层级。
Slack 提醒。在预期支出的 50/80/100% 时发出警报，以便工程师有时间规划。
简单的审批流程。经理批准层级升级，并快速传播。
成本检查技能和提示。一个仪表板技能，用于按需成本分解和实时状态行指导。

这些使工程师能够独立评估任务 ROI，同时缓解失控支出。

会话分析仪表板

虽然状态行会显示会话的总支出，但它无法让你了解成本驱动因素或可执行的效率优化步骤。通用指南提供了高层原则，但无法评估单个开发者的工作流。会话分析仪表板通过直接检查会话产物来弥合这一差距。

它直接内置于运行时中，无需任何设置或主动启用。执行成本仪表板技能会分析用户在所有使用的工具链中、本地及远程云沙箱里的全部会话轨迹。它不会生成一个汇总指标，而是标记出跨会话的 16 种不同反模式，并将每种模式与其财务影响和针对性修复方案配对。其中一些类别包括：

- 次优模型路由：在 Opus 上执行 Sonnet 即可轻松完成的简单多轮会话。
- 上下文窗口膨胀：大型 MCP 负载（例如 40KB 的响应）持续保留在上下文中，导致后续轮次产生重复计费。
- 缓存过期低效：长时间中断后恢复会话时，过期的提示缓存迫使以全价重建前缀。
- 提示初始化开销：在提供任何用户输入之前，预加载 100,000 个 token 的系统指令和工具定义。

图 12：会话级成本仪表板识别浪费模式和潜在节省空间。

下一步计划？

目前正在推进的计划包括：

- 扩展托管代理集群：对于每个新代理，我们都遵循一致的路线图：确定目标成果指标、构建评估基准、并找出帕累托最优模型。这种系统化方法旨在将 SDLC 的每个阶段提升到工厂成熟度模型的更高层级。
- 动态模型路由：我们正在扩展跨多种编程语言、代码仓库和代理形态的基准覆盖范围。鉴于模型能力差异巨大，有效的模型路由高度依赖于全面的评估。
- 深化上下文图集成：我们正在为更广泛的自主代理解锁图查询能力。
- 将会话分析演进为实时开发者指导：通过从周期性批量检测反模式转向持续轨迹监控，我们旨在直接向工程师提供个性化的实时效率建议。
- 持续技能改进：我们正在研究一种自动化方式，用于记录代理技能执行中的小问题，并根据收集到的轨迹自动生成技能更新。

结论

管理和遏制不断上升的 AI 编码成本同样是一项可解决的工程挑战。通过消除浪费的、零价值的 token 消耗，而不是仅仅依赖更低的单价或降级工具，我们将使用量扩展了 7 倍，同时降低了所有指标的单位成本，并提升/保持了输出质量。

核心战略转变是从交互式开发者工作流转向完全托管的代理。将 SDLC 工作负载迁移到托管环境，可以完全掌控模型路由、执行工具链和运营支出。优化一支由专用托管代理组成的集群（每个代理都配有专属评估基准和帕累托高效模型），本质上比优化数千名工程师的个人终端会话更具成本效益和可扩展性。
