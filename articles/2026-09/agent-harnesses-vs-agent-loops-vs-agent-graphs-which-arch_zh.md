Agent 框架 vs. Agent 循环 vs. Agent 图：你应该构建哪种架构？

大多数人在构建 Agent 时顺序搞错了。

他们从提示词开始。

然后是工具。

然后是五个子 Agent。

然后是一个仪表盘。

然后是一个“记忆层”。

两周后，他们得到了一个昂贵的聊天机器人，有时能打开正确的标签页。

真正的问题不是：

我应该用哪个模型？

而是：

当事情出错时，什么架构应该控制模型？

因为每个严肃的 Agent 最终都必须处理同样的问题：

工具失败
模型丢失任务
上下文变得过时
某个操作需要审批
重试让情况变得更糟
两个任务应该并行运行
一个长工作流在重启后存活
没人知道为什么最终答案被接受了

有三个有用的答案：

Agent 框架（Agent Harnesses）
Agent 循环（Agent Loops）
Agent 图（Agent Graphs）

它们不是竞争对手。

它们解决同一系统的不同层面。

简短回答

当你需要一个可靠执行环境来支撑一个能力强的 Agent 时，使用 Agent 框架。

当任务是迭代式的，并且每次尝试后都能检查成功与否时，使用 Agent 循环。

当工作流有分支路径、并行工作、持久状态、审批或多个可能路线时，使用 Agent 图。

错误在于把图当作更聪明的提示词。

或者把循环当作生产系统。

或者把框架当作“只是一个系统提示词”。

首先：什么是 Agent 框架？

Agent 框架是模型周围的运行环境。

模型不是 Agent。

模型是推理引擎。

框架决定：

存在哪些工具
Agent 被允许做什么
它的文件和状态存放在哪里
什么算成功
什么被记录
何时停止
何时重试
何时必须由人类批准某个操作

Claude Code、Codex 风格的编码 Agent、浏览器 Agent、研究 Agent 和自主工作者都需要一个框架。

没有框架，你基本上就是给一个非常聪明的实习生终端访问权限，然后希望它读 README。

一个好的框架把模型从：

“这里有一些建议”

变成：

“这里是确切的任务、环境、工具契约、验证规则、预算和最终产物。”
框架模式
text
输入
 ↓
任务契约
 ↓
工作区 + 状态
 ↓
工具 + 权限
 ↓
模型执行
 ↓
验证器
 ↓
产物 / 重试 / 升级

重要的部分是任务契约。

任务契约应该定义：

text
目标：
修复失败的 API 端点。

允许的文件：
server/routes/*
tests/api/*

成功条件：
npm test -- api 必须通过。

约束：
- 不要修改数据库模式。
- 不要更改公共响应字段。
- 在 3 次修复尝试失败后停止。

输出：
一个补丁、测试结果和简洁的解释。

这听起来显而易见。

但大多数“Agent 系统”仍然给模型一个巨大的模糊提示词，然后奇怪它为什么编辑无关的文件。

何时框架是正确的选择

在以下情况下构建框架：

一个 Agent 能完成大部分工作
工具比多 Agent 协调更重要
你需要可靠的日志和产物
Agent 接触文件、浏览器、API 或资金
任务有明确的成功条件
你需要对令牌、时间、权限或重试次数设限

示例：

仓库内的编码 Agent
必须引用来源的研究 Agent
可以查询内部工具的支持 Agent
在写作前必须验证产品声明的内容 Agent
管理文件、模型和 GPU 作业的本地 AI 工作者
主要好处

框架让行为可重复。

同一个模型在拥有以下条件时看起来会聪明得多：

干净的工作区
狭窄的工具权限
明确的完成定义
来自测试的结构化反馈
之前尝试的持久记录

提示词很重要。

但环境更重要。

框架的失败模式

常见的失败是构建一个“上帝框架”。

一个 Agent 获得：

30 个工具
每个仓库文件
所有公司文档
无限上下文
没有成本上限
没有明确的停止规则
没有验证器

它不会变得自主。

它会在规模上变得混乱。

框架应该减少选择，而不是创造更多选择。

给 Agent 最小的能完成任务的环境。
第二：什么是 Agent 循环？

Agent 循环是一个重复的周期：

尝试任务
观察结果
验证它
把失败变成有用的反馈
重试或停止

基本形式很简单：

text
计划
 ↓
行动
 ↓
观察
 ↓
验证
 ↓
修复或完成

这是大多数优秀编码 Agent 背后的架构。

模型写代码。

测试失败。

框架返回失败。

模型修复相关部分。

测试再次运行。

重要的不是重试。

重要的是反馈的质量。

糟糕的循环
text
Agent 尝试
 ↓
失败
 ↓
“再试一次”
 ↓
Agent 随机更改东西
 ↓
以不同方式失败
 ↓
重复直到预算耗尽

这不是自我改进。

这是昂贵的恐慌。

好的循环
text
Agent 提出行动
 ↓
确定性验证器运行
 ↓
失败被定位
 ↓
Agent 只接收相关证据
 ↓
Agent 选择修复或停止
 ↓
结果被存储

循环需要一个独立于模型的验证器。

对于代码：

测试
类型检查
代码检查
构建输出
截图对比
API 契约测试

对于研究：

来源链接
引用提取
新鲜度检查
声明到来源的匹配

对于内容：

事实对照文档验证
钩子匹配实际证据
没有不支持的数字
没有重复之前帖子的角度

对于操作：

数据库记录已更改
API 返回了预期负载
作业已完成
人类已批准不可逆步骤
何时循环是正确的选择

在以下情况下使用 Agent 循环：

任务可以反复检查
Agent 需要不止一次尝试
每次尝试创造新证据
工作流大多是线性的
有一个核心目标

示例：

修复一个 bug 直到测试通过
研究一个声明直到两个来源确认它
生成一篇文章直到事实门控通过
从 PDF 提取表格直到模式验证成功
针对已知评估集优化提示词
主要好处

循环给模型带来后果。

没有循环，模型产生文本。

有了循环，模型对着现实运作。

这个区别就是一切。

循环的失败模式

当循环没有硬边界时，它就变得危险。

你需要：

text
最大尝试次数 = 3
最大工具调用次数 = 20
最大成本 = $X
最大运行时间 = 10 分钟
如果 = 没有可衡量的进展，则停止
如果 = 破坏性操作或模糊需求，则升级

永远不要让 Agent 无限重试，因为“它可能会想明白”。

如果验证器说了三次同样的话，系统需要不同的策略，而不是模型第四次道歉。

第三：什么是 Agent 图？

Agent 图是一个具有明确状态和路由的工作流。

而不是：

text
开始 → 做任务 → 完成

你可以定义：

text
开始
 ↓
分类任务
 ├── 简单请求 → 直接回答
 ├── 编码任务 → 编码循环
 ├── 研究任务 → 来源收集
 ├── 敏感操作 → 人类审批
 └── 模糊任务 → 澄清

当工作流不再是一个线性循环时，图就很有用。

它不是关于使用更多 Agent。

它是关于让系统的可能路径变得明确。

真正的图有状态

关键思想不是节点。

是状态。

一个生产级 Agent 需要知道：

它在处理什么任务
它已经检查了哪些来源
它调用了什么工具
哪些步骤成功了
什么失败了
什么需要审批
重启后从哪里恢复
它走了哪个分支以及为什么
text
state = {
 任务 ID,
 目标,
 当前节点,
 证据,
 工具结果,
 重试次数,
 审批,
 预算,
 状态
}

这就是为什么图对长时间运行的 Agent 变得有用。

你可以暂停它们。

恢复它们。

重放它们。

审计它们。

何时图是正确的选择

在以下情况下使用 Agent 图：

多种任务类型
条件路由
并行研究或执行
审批检查点
持久化任务
多个职责明确分离的代理
需要不同策略的重试
可在重启后继续运行的长时间任务

示例：

客户支持运营代理
包含研究、验证、撰写和媒体阶段的内容引擎
包含规划器、执行器、测试循环、审查器和部署门禁的编码平台
包含风险检查和人工审批的金融工作流
多源情报系统
核心优势

图让失败变得可见。

不再只是说：

“代理失败了。”

你可以说：

“源验证节点失败，因为没有主要文档确认该声明。编写器从未运行。”

这就是生产系统应有的失败方式。

图的失败模式

常见的错误是过早地把一切都图化。

人们构建：

一个规划代理
一个研究代理
一个批评代理
一个摘要代理
一个评审代理
一个监督代理
一个记忆代理
一个包含18个节点的图

……而这项任务本可以由一个模型、两个工具和一个验证器完成。

图并不代表复杂精妙。

图代表的是运维复杂性。

每个节点都会增加：

延迟
令牌成本
需要维护的状态
另一个故障点
另一个上下文漂移的场所

只有在路由或持久化能带来真正优势时才使用它。

过度设计

你究竟应该构建什么？
如果你符合以下情况，请构建框架（Harness）

你有一个代理。

它需要工具。

它需要清晰的工作区。

它需要护栏。

它需要完成定义。

text
在以下情况下使用框架：
- 一个能力足够的模型可以解决该任务
- 任务基本是自包含的
- 你需要文件、浏览器、Shell 或 API
- 你可以直接验证输出

示例：

“修复我仓库中的这个问题。”
“研究这个产品并起草一篇经过验证的文章。”
“把这些笔记变成一篇文章。”
“根据规范审查这个 PR。”
如果你符合以下情况，请添加循环（Loop）

你的代理可以行动，但无法在第一次尝试时可靠地完成。

text
在以下情况下添加循环：
- 任务有可衡量的成功标准
- 测试或验证可以自动运行
- 失败证据可以指导修复
- 重试比人工干预更便宜

示例：

测试驱动的编码
截图到 UI 的实现
声明验证
结构化提取
具有已知预期结果的浏览器工作流
如果你符合以下情况，请添加图（Graph）

你的工作流现在有多条合法路径。

text
在以下情况下添加图：
- 不同的请求需要不同的流水线
- 工作应该并行运行
- 任务可以暂停和恢复
- 某些操作需要审批
- 你需要审计追踪
- 单一循环正在变得难以阅读

示例：

生产级内容引擎
自主客户运营
研究加发布工作流
多仓库编码系统
金融或合规工作流
最佳架构通常是分层堆叠

最强大的系统不会只选择一种。

它们会分层叠加。

text
图（GRAPH）
 决定工作流向何处

框架（HARNESS）
 为每个执行者提供合适的环境

循环（LOOP）
 改进单个任务直到通过验证

例如，内容引擎可以这样工作：

text
收到主题
 ↓
图：对主题进行分类
 ↓
框架：研究代理获得网络、文档、来源规则
 ↓
循环：对照主要来源验证事实声明
 ↓
框架：编写者只接收已验证的证据
 ↓
图：路由到草稿、审批或拒绝

这远比一个庞大的提示词要强大得多，那个提示词说：

“深入研究这个，找到来源，验证一切，写一篇爆款文章，选择视频，记住我的风格，不要产生幻觉。”

使用技术黑板风格，不要有 UI 线框图。

实用的决策框架

在添加另一个代理之前，先问这五个问题：

text
1. 一个模型能否在正确工具的帮助下解决这个问题？
 → 构建框架。

2. 每次尝试后能否衡量成功？
 → 添加循环。

3. 失败是否会产生有用的、结构化的反馈？
 → 在添加代理之前先改进验证器。

4. 工作流中是否存在多条有效路径？
 → 考虑使用图。

5. 任务是否必须在重启、审批或长时间等待后继续存在？
 → 使用持久化的图状态。

如果你无法回答什么能验证成功，你还没有准备好添加更多代理。

如果你无法解释一条路由为什么存在，你还没有准备好使用图。

如果你无法定义工具权限，你还没有准备好实现自主性。

真正的要点

大多数代理失败不是因为模型太弱。

而是因为系统给了模型：

模糊的目标
无限的上下文
不可靠的状态
薄弱的反馈
没有停止条件
没有任务完成的证明

从框架开始。

当你能验证工作时，添加循环。

只有当工作流真正产生分支时，才添加图。

这就是你从一个“有时能做点事”的聊天机器人，走向一个真正可以信赖的代理系统的方式。
