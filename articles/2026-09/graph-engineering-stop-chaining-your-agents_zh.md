图工程：别再链式编排你的代理

几乎每一个我打开过的多步骤代理都是一个队列。第一步、第二步、第三步，每一步都礼貌地等待上一步完成。而一旦你仔细看，大约一半的步骤根本没有什么可等待的。

它们不路由，不拆分，也不并行运行任何东西。它们只是排成一队，一个头、一个上下文、一次只做一件事，直到窗口填满，代理悄悄忘记了自己最初在做什么。

这里有一个没人会明确告诉你的点。提示词是一个句子。循环是一个周期。框架是代理站立的地板。但工作本身的形状——什么在什么之前运行，什么可以同时运行，什么真正必须等待其他所有东西——这个形状是一个图。节点负责思考，边负责传递结果。

Claude Code 直接提供了构建这些图的工具：动态工作流。Claude 编写一个纯 JavaScript 编排脚本，然后生成一个协调的子代理舰队来执行它。协调本身不消耗任何模型 token，因为它是代码，而不是另一段对话。

这是我用来将单个文件代理转变为跨舰队扇出、检查自身发现、并最终落在一个单个代理无法容纳的结果上的 14 步路线图。

概览

1. 节点是任务，边是流动的东西。
2. 你的线性脚本已经是一个图，只不过是个糟糕的图。
3. 每个节点都要有契约。
4. 每条边都要有数据契约。
5. 用 parallel() 扇出。
6. 在屏障处扇入，并且只在必要时这样做。
7. 菱形：拆分、工作、合并。
8. 在运行时用条件路由边。
9. 在边上放置验证器。
10. 隔离节点，让一次失败保持局部。
11. 添加循环，但要让它收敛。
12. 在节点间分层使用模型。
13. 拓扑结构就是你的成本和延迟。
14. 让 Claude 为你绘制图。

01. 节点和边，或者说为什么“然后”不是依赖

一个图恰好有两个部分，把它们弄清楚就能消除大部分困惑。

节点是工作单元。一个代理、一个有限的任务、一个输入进、一个输出出。

边是依赖。它表示这个节点的输出馈送给那个节点的输入。这就是全部定义。

几乎每个人都会犯的错误是把“然后”当作边。“总结这个文件，然后告诉我天气”中没有任何边。天气不消费总结。这是两个断开的节点，线性脚本毫无理由地把它们链在一起。

要问的问题。对于代理中的每个“然后”：下一步是否真的读取上一步的输出？如果没有，那里就没有边，等待纯粹是浪费。

纯文本
把它画成方框和箭头。一个方框是一个 agent()
调用。一个箭头是一个变量，它离开一个调用的
返回，进入另一个调用的提示词。如果你无法画出
箭头，如果没有变量跨越，那两个方框
就是独立的。这种独立性正是你
将在本文剩余部分利用的东西。
02. 你的线性脚本是一个退化图

当你把代理写成“做 A，然后 B，然后 C，然后 D”时，你已经画了一个图。你画的是最糟糕的一种：一个单一的不分支的链，每个节点恰好有一条边进、一条边出。

它能运行。但它运行得也慢，而且坏得很厉害，因为链没有冗余。如果 C 停滞，D 永远不会发生，A 产生的所有东西都卡在上游无处可去。

这里第一个真正的技能是重新绘制链。拿起你的线性代理，走一遍每个箭头，问步骤 01 中的问题。在实践中你会发现有两三个箭头根本不携带任何数据。它们存在只是因为那是你碰巧输入的顺序。

剪掉那些箭头，链就会横向坍塌成更宽的东西：一把可以同时运行的独立节点，汇入一个需要所有它们的单一节点。

03. 给每个节点一个契约

一个你无法推理的节点是一个你无法并行化的节点。解决办法是契约：有界输入、有界输出、恰好一个任务。

输入是节点读取的任何东西，显式传入。绝不从它碰巧所在的共享窗口假设。输出是定义好的形状，理想情况下经过验证，这样下一个节点无需猜测就能消费它。

在工作流中，你通过模式来强制执行这一点。当你给 Claude 一个带有 JSON 模式的 agent() 调用时，它生成的子代理被迫返回经过验证的结构化数据。验证发生在工具调用层，所以 Claude 在不匹配时会重试，而不是给你需要解析和祈祷的自由文本。

json
// 一个带有真实契约的节点：有界输入、验证输出、
一个任务。
const FINDING = {
 type: 'object',
 additionalProperties: false,
 properties: {
 title: { type: 'string' },
 url: { type: 'string' },
 impact: { type: 'string', enum: ['high', 'medium',
'low'] },
 },
 required: ['title', 'url', 'impact'],
};

const result = await agent(source.prompt, {
 label: `research:${source.key}`,
 schema: FINDING, // 强制验证
结构化输出
 agentType: 'general-purpose',
});
// result 现在是下一个节点可以信任的形状，而不是自由文本。

这就是 Claude 能接入图的节点和只能靠人类阅读输出的节点之间的全部区别。

04. 边也是数据契约

边不是“B 在 A 之后”。它是一个关于什么跨越的承诺：A 产生这个形状，B 被构建来消费这个形状。用数据而不是顺序来命名你的边，两件事会变得容易得多。

你可以立刻判断边是否真实，也就是说数据是否真的在移动。而且只要形状保持不变，你可以交换任一端上的节点，而不触及图的其余部分。

在实践中，边存在于纯 JavaScript 中。扇出和综合之间的归约步骤——展平、去重、过滤——只是作用于节点返回形状的代码。

不需要代理。这是图思维带来的一个安静胜利：人们烧掉大量模型 token 的东西实际上往往只是一条边，而边是免费的。

json
// 诱人的做法：生成一个代理来“合并结果”。不要。
// 如果合并意味着展平和去重，那就是 flatMap
加一个 Set。
// 确定性、即时、零 token。
const flat = collected.flatMap((c) => c.items);
const clean = [...new Map(flat.map((i) => [i.url, i])).
values()];

把代理留给判断。不要用于管道。一个每条边都是代理的图，是在为自己的布线付租金。

05. 用 parallel() 扇出

这是为其他一切买单的动作。当你有 N 个独立节点、N 个要检查的来源、N 个要审查的文件、N 条要审计的路由时，你不要链式编排它们。

你告诉 Claude 扇出它们并同时运行。在工作流中，这就是 parallel()：Claude 接受一个 thunk 数组，为每个 thunk 生成一个子代理，并发运行它们，然后把结果数组交还给你。

两个细节让它健壮。首先，parallel() 是一个屏障，所以它会等待每个 thunk 完成才返回，下一阶段总是看到完整集合。其次，抛出的 thunk 会解析为 null，而不是拒绝整个批次，所以一个不稳定的代理不会让整个运行沉没。

在输出时始终使用 .filter(Boolean)。并发上限大约是你的核心数，溢出会排队，所以你可以交给它一百个 thunk，它们都会完成，只是一次几个。

json
phase('Research');

// 九个来源，九个代理，同时进行。
const raw = await parallel(
 SOURCES.map((s) => () =>
 agent(s.prompt, {
 label: `research:${s.key}`,
 phase: 'Research',
 schema: ITEM_SCHEMA, // 每个节点返回
验证过的 JSON
 agentType: 'general-purpose',
 }),
 ),
);

const collected = raw.filter(Boolean); // 丢弃失败代理的 null

扇出逻辑存在于 Claude 编写的代码中，而非模型对话中。Claude 自身的上下文永远不会同时容纳九个来源。每个子代理各自持有自己的上下文，只有最终答案会返回。这正是工作流能够扩展到数十甚至数百个子代理而不会淹没会话的原因，而且编排层不消耗任何成本，因为它不是 Claude 的又一轮思考。

06. 在屏障处汇聚

扇出只有在有东西将其汇聚时才具有价值。汇聚节点是你的边汇合之处，一个代理或一段代码同时看到所有上游结果，并执行真正需要完整集合的操作：跨来源去重、按影响排序、如果所有结果都为空则提前退出。

这是屏障值得消耗其墙钟时间的唯一位置。

让图保持快速的规则：仅当某个阶段确实需要所有先前结果在一起时，才使用屏障。跨所有来源去重就符合条件。

```json
// 这条边：纯 JS，无代理，零 token。
const flat = collected.flatMap((c) => c.items);
log(`Collected ${flat.length} items`);

phase('Curate');
// 屏障节点：需要完整集合才能去重和排序。
const curated = await agent(
  `按影响去重并排序这些内容：\n${JSON.stringify(flat)}`,
  { phase: 'Curate', schema: CURATED_SCHEMA },
);
```

仅仅展平一个列表不是屏障，而是一条边，直接内联处理即可。判断标准极其简单：如果你写了并行、然后转换、再并行，而中间那个转换没有跨条目依赖，那你就应该使用管道，完全跳过屏障。

07. 菱形拓扑：拆分、处理、合并

把扇出和汇聚放在一起，你就得到了每个严肃代理图的核心拓扑结构：菱形。

一个节点拆分任务。多个节点并行执行工作。一个节点合并结果。这就是市场扫描、依赖审计、代码审查、研究报告背后的形态。更换来源和提示词，同一个骨架就能适配所有这些场景。

这种标准形态值得牢记：扇出、缩减、综合。扇出以获取广度。用纯代码缩减以压缩。用最终代理综合以撰写答案。

一旦你能看到菱形，你就不再问"如何让我的代理执行更多步骤"，而是开始问"拆分在哪里，合并在哪里"。第二个问题才是真正能扩展的问题。

08. 用条件在运行时路由边

并非每个图都是固定的。有时走哪条边取决于节点发现了什么。路由器节点检查结果并决定触发哪条下游路径：对工单分类，然后分支到正确的处理程序。检查 diff 大小，然后要么做快速审查，要么启动全面审计。

在工作流中，这只是在节点的验证输出上写一个 JavaScript 的 if 或 switch，因为你的控制流存在于代码中。

```json
// 路由器节点：代理分类，代码选择边。
const { severity } = await agent(`对此 diff 的风险进行分类：\n${diff}`, {
  schema: {
    type: 'object',
    properties: { severity: { type: 'string', enum: ['low', 'high'] } },
    required: ['severity'],
  },
});

let review;
if (severity === 'high') {
  // 重路径：完整并行审计
  review = await parallel(FILES.map((f) => () => agent(`Audit ${f}`)));
} else {
  // 轻路径：一次快速检查
  review = await agent(`Quick review of ${diff}`);
}
```

这正是确定性从限制变成特性的地方。路由器的决策可以由 Claude 驱动，子代理负责分类。路由是 Claude 编写的代码，因此对于相同的分类，每次运行方式完全相同。

你在节点获得 Claude 的判断力，在边获得脚本的可靠性。不会出现"Claude 今天决定跳过审计"这种意外，因为跳过必须被写进图中，而它并没有。

09. 在边上放置验证器

图的真正杠杆不在于你获得更多代理，而在于你可以围绕它们构建结构以产生信心。

验证器节点位于边上，在结果被允许进入下游之前，它的唯一任务就是尝试推翻发现。如果它存活下来，就通过。如果没有，它就永远不会到达你的答案。

值得掌握的三种模式：

- 对抗性验证。对每个发现，生成 N 个独立的怀疑者，提示他们反驳它，只有当多数存活时才保留。
- 多视角验证。给每个验证器自己的视角——正确性、安全性、能否复现——因为多样性能够捕获 N 个相同检查永远无法发现的失败模式。
- 评审团。从不同角度生成 N 个尝试，用并行评审打分，从胜者中综合，同时嫁接亚军的精华部分。

这正是让一个真实团队将 Bun 运行时移植成功并直接将对抗性代码审查嵌入循环中的模式。

10. 隔离节点，让单个失败保持局部化

在链中，失败会级联。C 挂了，D 永远不会运行，整个流程停止。在图中，失败应该被限制在它自己的节点内。

其中一部分已经是事实：在 parallel() 中抛出的 thunk 会解析为 null，所以八个正常代理仍然返回结果，而那个失败的代理被剔除。你的 .filter(Boolean) 就是隔离机制。设计每个汇聚节点时都要容忍缺失输入，而不是假设完整集合。

更微妙的失败是节点互相踩踏。当代理并行写入文件时，它们会发生冲突。

解决方案是隔离：worktree。每个代理在自己的 git worktree 中运行，在沙箱中完成工作，最后干净地合并。仅在节点真正并行写入时才使用它。它是针对特定拓扑的安全带，而不是每次运行的默认开销。

11. 添加循环，但让它收敛

有时你直到进入任务内部才知道工作量有多大。未知规模的发现。一次 bug 扫描发现一个 bug 又暴露出三个。这就需要循环，一条受控的边回到更早的节点。

危险显而易见。永不收敛的循环就是无限循环，不断生成代理直到预算耗尽。

能够收敛的模式是"循环直到枯竭"：持续生成查找器，直到连续 K 轮没有发现新内容，然后停止。而决定成败的细节——几乎每个人第一次都会搞错——是你对什么进行去重。

对所有已见过的内容去重，而不仅仅是对已确认的结果去重。否则被拒绝的发现每轮都会回来，循环永远不会枯竭，你就造了一台永远花钱重新发现同样死胡同的机器。

```json
const seen = new Set(); const confirmed = []; let dry = 0;

while (dry < 2) { // 连续 2 轮为空后停止
  const found = (
    await parallel(FINDERS.map((f) => () => agent(f.prompt, { schema: BUGS })))
  ).filter(Boolean).flatMap((r) => r.bugs);

  const fresh = found.filter((b) => !seen.has(key(b)));
  if (!fresh.length) { dry++; continue; } // 没有新内容，接近枯竭
  dry = 0;
  fresh.forEach((b) => seen.add(key(b))); // 对 SEEN 去重，而非 confirmed

  // 多视角验证：每个新发现都要赢得自己的位置
  const judged = await parallel(fresh.map((b) => () =>
    parallel(['correctness', 'security', 'repro'].map((lens) => () =>
      agent(`Judge "${b.desc}" via ${lens}. Real?`, { schema: VERDICT })))
      .then((v) => ({ b, real: v.filter(Boolean).filter((x) => x.real).length >= 2 }))
  ));

  confirmed.push(...judged.filter((v) => v.real).map((v) => v.b));
}
```

12. 在节点间分层使用模型

并非每个节点都需要你最好的模型。图让这一点变得显而易见，而单个代理永远做不到：有些节点是有界且重复的——提取这个字段、分类这个工单。其他节点承载真正的判断力——综合报告、裁决发现。

在较便宜的模型上运行枯燥的节点，把昂贵的 token 花在真正需要判断力的地方。

在流程中，Claude 生成的每个子代理默认继承你的会话模型，除非脚本覆盖设置，因此默认情况下，大规模运行完全按你的会话层级计费。单个 `agent()` 调用上的模型选项告诉 Claude 仅将该节点路由到其他位置。

在大规模运行前检查 `/model`，然后让 Claude 将扇出节点的重复节点路由到更便宜的模型，同时将合并节点保持在顶层。这就是将高令牌消耗的图转变为经济型图的关键杠杆，而无需改变其形状。

13. 拓扑结构决定成本与延迟

图的形状并非装饰性元素。它是影响挂钟时间的最大杠杆。几乎每个人都会在 `parallel()` 与 `pipeline()` 之间犹豫不决。

`parallel()` 屏障使所有内容等待最慢的节点完成后，下一阶段才能开始。`pipeline()` 则让每个条目独立流经所有阶段，没有屏障，因此条目 A 可以处于阶段 3，而条目 B 仍在阶段 1。快速条目提前完成，而不是在慢速条目后面空等。

默认使用 `pipeline()`。仅当某个阶段确实需要同时获得所有先前结果时才使用屏障：跨集合去重、基于总数的提前退出、将一项发现与所有其他发现进行比较的提示。

“代码更干净”和“阶段看起来分离”都不是理由。屏障延迟是真实存在、可测量且被浪费的时间。分离不等于同步。

| 形状 | 使用场景 | 代价 |
|------|----------|------|
| 链式 | 每一步真正读取上一步的输出 | 最慢的可能运行，一个停滞导致全部失败 |
| `parallel()` 扇出 | N 个独立任务，下一阶段需要全部结果 | 所有人等待最慢的节点 |
| `pipeline()` | N 个独立任务流经相同阶段 | 几乎无代价，这是你的默认选择 |
| 菱形 | 广度优先，然后一个合并答案 | 在合并处有一个屏障，这是值得的 |
| 条件分支 | 路径取决于节点发现的内容 | 分支前有一次分类调用 |
| 循环 | 你不知道任务规模有多大 | 如果永不收敛，支出将失控 |

14. 让 Claude 绘制图

最后一步是，对于你无法预先规划的任务，停止手动绘制图。

使用动态工作流，你描述目标，Claude 自行编写编排脚本：分解任务、选择扇出方式、生成协调的子代理舰队、综合结果。你最终得到一个针对**本次**运行量身定制的图，而不是一个你希望适用的固定图。

有三种进入方式。

在提示中说出“工作流”一词，Claude 就会为任务编写一个。

运行已保存或捆绑的工作流。`/deep-research` 是当前生产环境中实际运行的图：范围界定、并行搜索、抓取、对抗性验证、综合。这正是本文中的确切骨架。

开启 ultracode，Claude 会为会话中的每个重要任务规划工作流。当运行结果良好时，按 `s` 将其脚本保存到 `.claude/workflows/` 中。现在它受版本控制，可按名称重新运行，任何克隆仓库的人都可以启动该图。

```plaintext
> 运行工作流审计 src/routes/ 下的每个路由
是否缺少认证。
 为每个路由文件生成一个代理，然后在报告前
验证每个发现。
• Claude 编写了编排脚本 · 在后台启动...
 /workflows > auth-audit · 运行中
 ✓ 范围界定 1/1 2.1k 令牌 · 4秒
 ✓ 扇出 18/18 每个路由文件一个代理
 ○ 验证 11/18 每个发现 3 票怀疑者...
 ○ 综合 0/1 等待验证
 会话保持响应，舰队运行时你可以继续工作
```

本周值得构建的六个图

- 跨所有路由的安全扫描。每个路由文件一个子代理，各自寻找缺失的认证检查，然后通过验证器遍历确认每个发现后才进入报告。广度是单一上下文无法容纳的。

- 使用 `/deep-research` 生成带引用的报告。Claude 将你的问题拆分为不同角度，并行运行搜索，对来源去重，然后在写出任何内容之前用三个投票怀疑者对每个声明进行对抗性验证。

- 逐文件移植模块。将 Bun 上限缩小到你的仓库规模。Claude 将翻译扇出到各文件，将测试套件作为每个文件的关卡，并将失败循环回来，通过对抗性审查捕获单次遍历可能交付的损坏内容。

- 对差异的对抗性审查。Claude 根据差异大小路由：小改动获得一次快速遍历，大改动触发完整的并行审计，审查者从不同视角审查，然后由评审团综合裁决。

- 按计划进行的生态系统扫描。保存一次，永久重新运行。Claude 并行检查多个来源——发布、博客、讨论——在屏障处按影响排序，并撰写摘要。版本控制在 `.claude/workflows/` 中，可按名称启动。

- 未知规模的任务发现。你不知道里面有多少个 bug。Claude 并行运行查找器，将每个新发现与所有已见内容去重，验证幸存者，并持续循环直到两轮没有新发现。

为什么这真的很重要

这些步骤中的每一步都指向同一个底层事实。你的代理上限几乎从来不是模型本身，而是你交给它的工作形状。

链式结构迫使单一上下文容纳一切，单一故障使一切停止，每个快速步骤都要等待最慢的步骤。图将上下文分散到整个舰队中，将故障限制在节点内，并为你提供可以围绕其构建信心的结构：节点上的模式、边上的验证器、每次以相同方式运行的路由。

而编排层是代码。这是人们低估的部分。十八个代理之间的协调消耗零模型令牌，因为脚本不是对话。

这里真正重要的是什么

如果你只从本文带走三件事：剪掉不携带数据的箭头，默认使用 `pipeline()` 而不是屏障，以及针对你见过的所有内容去重，而不是仅针对你确认过的内容。

仅这三项就能让你的代理更快、更便宜、更难被破坏，远比在队列中再添加一个步骤有效。

线性代理从来不是上限。它只是每个人首先想到的形状，因为它符合我们的输入方式。一行、一个头脑、一次一件事。
