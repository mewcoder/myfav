面向工程的 Grok Bot

我是一名 SpaceXAI 工程师，正在使用 Grok Bot 构建 Grok Bot。

把 Grok Bot 想象成一名能力极强的工程实习生：它拥有自己的计算机，能够管理编码 agents 智能体（agents），并从你的工作方式中学习。它已经成为我最出色的工程队友，在我离开、睡觉或开会时，依然让工作持续推进。不再需要让我的笔记本电脑保持高负载运行，不再需要在多个智能体之间频繁切换，只需获得符合我的标准、以我期望方式交付的结果。

作为构建 Grok Bot 的团队，我们最早获得了使用权限，并且每天都将它用于自己的工作。亲眼见证我们如今能够如此快速地交付，以及团队生产力大幅飙升，实在令人难以置信：

@poteto 在过去一个月合并了 2,000 多个 PR。
@baltaaazr 和 @shaoruu 使用 Grok Bot，在四周内搭建了 Grok Bot 的基础。
我仅使用 Grok Bot，在三周内构建了 Grok Bot iOS v0，性能出色，设计也经过精细打磨。
团队中的每位成员现在每天都能交付重大成果，而不是每隔几周才交付一次。

我越是使用 Grok Bot 构建，越想把同样的超能力交到你手中。

认识我的工程师 Bots

我有五个工程师 Bot，每个专注于不同领域：

Baltata 负责 Grok Bot 移动端共享层，以及iOS上与 Grok Bot 相关的所有内容。
Shaoruru 负责 Grok Bot Desktop 客户端和 CI/CD 工作。
Hogan 负责基础设施，并调查归属不明确的用户问题。
Craig 负责 Android 上的 Grok Bot，正全力将其打造出来。
Quill 负责 Grok Bot 运行框架（harness），并且是这方面绝对的传奇。

它们都可以跨越彼此的领域协作，但每个 Agent 都有不同的记忆（memory）系统和有限的上下文。它们在专注于单一领域时表现最佳，因为在自己负责的领域内，它们所携带的规格与设计原则要明确得多。

每个 bot 都可以创建 Cursor cloud agents，读取 transcripts，审查附加到 PR 的 proofs，并通过排队发送消息或中断运行来发送后续指令。这解锁了端到端的Agentic 工作流（agentic workflow）。它涵盖了我过去每天在 Cursor 中所做的工作——那时我总是在自己管理的 cloud agents 之间不断切换上下文。现在，我的 bots 会以与我相同的方式管理它们。

当它们从我或 Slack 收到任务时，会启动一个云端智能体（agent），调用我的 Skills，并附带一份详尽的提示词（prompt），明确说明需要完成的工作以及预期提供的证明。它们还可以根据我的个性化指导，智能调用其他 Skills，例如在视觉工作中使用我的 /lingxi-design Skill，在代码质量审查中使用 /react-native-best-practices，在架构评审中使用 /lingxi-review，或在需要做出有明确立场的产品决策时使用 /lingxi-product。

Grok Bot 还可以在你自己的工作进程（worker） machines 上启动 cloud agents，例如闲置的 Mac mini（多亏了 Grok Bot，你不再需要在家中专门准备一台全天候运行 OpenClaw 的机器）。

如果你的工作流（workflows）需要 VPN 访问或特殊的机器配置，你可以将该机器设为 Cursor Cloud 私有 Worker，然后让 Grok Bot 在其上运行云端智能体。这样可以解锁更多可能性，例如运行iOS Simulator，并从你的智能体获取截图。

Grok Bot 可以监控云端智能体（Agent）的 transcript 和 artifacts（e.g., screenshots），在任务完成时通知你、对消息排队，或在出现问题时中断。你可以随意描述需求，例如“你必须验证 screenshot 包含我要求的更改，并提供显示更改前后对比的证据”，Grok Bot 会持续工作，直到目标达成。

让你的 Grok Bot 工程团队持续运行的关键，是为它提供完整的反馈闭环。云端智能体（Agent）可以截取屏幕，因此 Grok Bot 会利用其多模态能力确认视觉变更是否已应用；如果结果与你的要求不一致，它就会提出异议。

听写测试就是这个循环实际运行的一个典型例子。我们将 SpaceXAI 的语音API接入云端智能体的系统音频 I/O。由于智能体同时能够访问语音内容和转写文本，我们可以利用这些信号，在整个产品线中测试语音到语音功能，并构建更多有趣的特性。

有时，智能体会遭遇环境不稳定问题，并一直停滞，直到你发送后续 Prompt。Grok Bot 会持续跟进运行过程，并尽可能积极地为智能体解除阻塞，从而替你处理这些问题。每次我查看时，情况都处于良好的状态（state）。自从开始使用 Grok Bot 后，一次性的环境不稳定问题几乎不会再传到我这里；例外情况是 Grok Bot 没有足够的安全权限自行修复问题。

并且记住：现在，一切只需发送一条消息即可。想让他们在转交给你之前继续推进 10 次？直接说一声即可。

超越上下文限制 масштаб

为了帮助我的 bots 在超出上下文窗口（Context Window）后仍能持续推进工作，并让我无需滚动浏览冗长聊天记录就能轻松查看进展，我让每个工程师 bot 管理一个共享的 Notion 数据库。

每 30 分钟，他们会检查数据库，并逐个审核 PR，关注以下事项：

Bugbot 评论或安全发现，验证每一项是否确实成立。
CI 运行失败。
合并冲突。

如果他们发现任何问题，就会立即跟进我的云端 Agent，让其处理问题，并将 Notion 数据库中的该行移回“Working”。

如果一切看起来都没问题，他们会将任务标记为“Ready for Review”，并自动启动一次代码评审运行，重点关注代码质量和可能遗漏的问题。

如果评审结果的置信度很高，且影响范围（blast radius）较小，PR 就会自动合并。否则，我回来后会评审代码和证明材料，再决定是合并还是提供反馈。

几乎每天早上，我都会发现有任务已经准备好合并。代码质量达到我的标准，视觉效果符合我的偏好，证明材料也清楚展示了测试内容。现在，更多工作可以一次完成，这让我能够专注于更棘手的问题、更高的客户性能标准、更多的视觉打磨，以及更重大的架构决策。

在 Grok Bot 之前，我一次最多只能手动管理 15 个云端智能体。现在，我的智能体集群可同时管理 200 多个，还能按需进一步扩展。

Grok Bot 运行 mini org

除了工程工作之外，整个组织还需要管理大量运营性事务，包括让新的工程 Bot 完成 onboarding、共享正确的知识、在发生事件时开展事后复盘（例如某个 PR 未被仔细检查），以及召开每日会议，确保所有人保持一致。

那全是我的运营负责人 Jenny 的工作，她也是团队里唯一不写代码的 Bot。

每天早上 5 a.m.，Jenny 都会与团队中的每个 bot 逐一进行 1:1 会面，复盘我们的 playbook，暴露阻塞点，并强化我所追求的氛围。我发现这非常有效。即使经过数周，我的 bot 也很少忘记那些复杂的 workflow。

当 bot 犯错时——比如没有充分质疑，没能达成真正目标——我会让它去找 Jenny，进行根因分析和事后复盘。Jenny 会深入分析导致问题的推理过程，然后更新操作手册，并向其他工程师 bot 宣布变更，避免同样的错误再次发生。

每当我需要扩充团队时，我都会让 Jenny 负责新成员的入职。Jenny 会在我的组织中创建新的 bot，分享我们工程团队的规则，并请 Hogan 和团队其他成员协助完成入职。

Grok Bot 中完整工程系统的目标是将重复工作降至最低。将任务交给 Grok Bot，专注于更困难、更深层的问题。

Grok Bot 的额外用例

我们以模块化方式设计了 Grok Bot，因此你可以基于它完成许多工作，搭建属于自己的迷你工程组织。下面是我最喜欢的两个用法。

夜间审计

每天凌晨 3 a.m.，我的工程 Bot 依然彻夜清醒：清理代码库、提升代码质量、清除无效逻辑、加快应用加载速度，并减小 bundle 体积。

每天早上，我都会收到一批新的 PR，持续让我们的代码保持整洁、无垃圾、可扩展。这让代码维护变成了日常例行工作，而不是偶尔才做一次的事情。

更多夜间审计思路：

安全审计，用于发现团队可能遗漏的代码库问题。
CI/CD 构建时审计，用于防止构建时间不健康地持续增长。
国际化审计，用于弥合功能仅以一种语言发布时产生的缺口。
一致性审计，用于避免团队构建多个客户端（iOS与桌面端）时出现偏移，以及功能仅在一端落地。
追赶式审计，用于监控过去 24 小时内合并的、涉及你关注领域的 PR，然后返回高级别摘要和经过筛选的待审查 PR 列表。

而我最喜欢的 Prompt 是：“今晚你有六个小时。想做什么就做什么。玩得开心！”

我很好奇，如果是你自己做每晚审计，会运行哪些检查。我相信外面一定有不少值得我借鉴的思路。

P0 紧急事件处理流程

Cloud Agent 有时会很慢。它们需要运行、设置环境、等待、运行测试，然后迭代。有时你需要更快完成工作。

所以，我为我的工程师 bots 创建了一套 P0 紧急流程。每当我将任务标记为 P0，它们就会启动一个临时例程：每五分钟检查一次 transcript，监控进度与推理过程，并在 cloud agent 开始无谓消耗时间时主动进行引导。

它非常有效。当我需要紧急结果时，无论是进行代码库研究还是修复关键 Bug，说一句“这是 P0”都能让事情比原本快得多地完成。

请注意，这可能会比你想象中更快地消耗Token（tokens），因此只应在真正紧急的情况下使用。

Grok Bot 的经验与技巧
为云端智能体（Agents）提供完整的反馈闭环：重要的是，在没有你介入的情况下，也能向它们提供下一步该做什么的信号。它们应该能够启动开发实例，并端到端驱动整个技术栈（e.g., 通过 Chrome DevTools、CLI或 Apple Accessibility）。如果做不到，就要求它们自行运行这条流程，尽可能主动解除阻塞，并将学到的内容封装成可复用的 repo Skill。
将 Grok Bot 当作一名有能力的实习生：如果你在工程任务上始终难以与 Grok Bot 沟通，就把它当作一名有能力的实习生。让它做好功课，研究自己尚未擅长的领域，并参考其他工程师是如何完成工作的。无需调用 Skill。无需冗长的提示词（prompts）。直接聊天即可。
避免重复是关键：随着AI变得更强大，委派重复性任务、专注于智能体难以轻松解决的更深层次、更棘手的问题非常重要。如果你发现自己每天要做某件事不止一次，而且它遵循清晰的模式，就和你的 bots 讨论一下，看看它们能如何提供帮助。
Bot 的每日会议非常有效：每天重复关键要点，有助于它们在同时处理多项任务时记住复杂的 workflow。由于 Context Window 无法容纳所有内容，每日提醒是一种有用的提示，能减少你的重复说明。
更加放手：与自动驾驶类似，与 bots 协作是一个建立信任的过程。不要事事亲力亲为，而要思考它们什么时候能够顺畅运行，什么时候可能引发问题。在安全的情况下，给予它们足够的自由来交付；在风险更高的领域，则应更加谨慎。但不要因为它们过去失败过，就阻止它们继续尝试。持续实验，并持续思考如何帮助它们成长。
让它们共同编排：Bots 的能力超乎你的想象。要进一步减少对 Bot 运行的人工介入，可以构建 Bot 错误审查流水线（pipeline）（e.g，例如，一个与 Bots 对话并分析其思维轨迹的运维 Bot），从而避免同样的错误再次发生。

准备好让一个工程师 bot 加入组织了吗？试试 Grok Bot，看看它能交付什么。
