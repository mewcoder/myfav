Harness 工程（Harness Engineering）：取代了 2026 年提示词工程（prompt engineering）的技能

2024 年，核心技能是编写更优的提示词（prompts）。2025 年，核心技能是提供更优质的上下文。到了 2026 年，两者都不再是瓶颈所在。

瓶颈在于模型周围的一切：谁为它提供工具、谁检查其工作、它能记住什么、它被允许操作什么，以及是否有人能看到它的行为。这一层现在有了一个名字。它被称为运行框架（harness）。

每一轮浪潮并未取代前者，而是将其吸纳。上下文工程（Context engineering）吸收了提示词工程：你给模型喂什么，比你如何措辞提问更重要。Harness 工程则吸收了二者：Harness 决定加载何种上下文、发送何种提示词（prompt），并额外增加了七项单独靠提示词或上下文无法实现的能力：工具控制、验证、记忆（memory）、权限、可观测性（observability）、路由和反馈。

88% 的企业级AI智能体（agent）项目无法进入生产环境。失败的原因几乎从不是模型本身。问题出在上下文腐化、缺少安全护栏（guardrail）、没有状态（state）持久化，或是反馈回路从未闭环。使用相同模型但采用不同运行框架（harness）设计的两个团队，会得到截然不同的结果。决定成败的是运行框架（harness），而非模型。

运行框架（Harness）究竟是什么

模型蕴含原始智能。运行框架（Harness）使这份智能变得可靠。它是连接模型与现实世界的执行层：负责工具分发、验证、记忆、权限与日志记录。

一个生产级 Harness 有七个层级。每一层都防止一类不同的故障。

1. 工具编排

最重要的一条规则：永远不要让模型直接调用工具。模型返回结构化的工具调用（tool call）（函数名、参数）。运行框架验证模式（schema），检查权限，执行调用，并将结果注入回模型。这能防止提示词注入升级为任意代码执行。

这是草稿-提交模式。危险操作会先被草拟，然后显式地提交执行。模型建议“删除此文件”。Harness 会暂存该操作并请求确认。只读操作会立即通过。写入操作则需要等待。

无论是成功的API响应、权限拒绝还是超时（timeout），智能体总会收到一个结构化的观测结果。没有悬而未决的承诺，没有静默的失败。运行框架将每次工具交互都转化为一个清晰的请求-响应周期供智能体推理，而不是让智能体去解析原始的 shell 输出并猜测发生了什么。

2. 验证循环

每一个生产级 Harness 都将执行者（Maker）与审查者（Checker）分开。编写代码的模型在评判自己的作业时往往过于宽松。用另一套指令进行第二次检查，能捕获第一次运行中自我合理化的漏洞。

真实案例：2026年4月，Claude Code出现质量下降问题。Anthropic 将其追溯到三个独立的运行框架层面变更：推理强度降级、一个丢弃思考历史的缓存错误，以及一个过度限制冗余性的提示词。这些都不是模型问题，而是运行框架问题。模型本身是相同的。是外围系统的变化导致了质量崩溃。Anthropic 发布了完整的复盘报告。教训不是“修复模型”，而是“你的运行框架就是你的产品质量，请以相应态度对待它。”

验证循环未必昂贵。一个快速、廉价的模型即可处理大部分检查：是否通过编译？测试是否通过？变更范围是否在限定内？仅在廉价模型缺乏足够推理深度时，才将需要判断力的任务留给昂贵的模型。关键在于分层分工本身，而非验证器的成本高低。

3. 上下文与记忆（Context & Memory）

上下文工程（Context Engineering）告诉我们，你向模型提供什么内容远比如何提问更重要。Harness 工程则更进一步：它决定自动将什么内容送入上下文窗口（context window），而不是依赖人类每次都能做对。

生产级运行框架（Harness）会在对话轮次之间压缩上下文。它不会将整个对话历史塞入每次调用。它会总结已完成的子任务、丢弃已解决的工具输出，并仅保留当前步骤所需的内容。若无此机制，长时间运行的智能体（agents）将填满其上下文窗口（Context Window），开始丢失信息，且每一个推理步骤都会变得更差。

记忆的工作方式与此相同。运行框架（Harness）会持久化关键信息（CLAUDE.md、STATE.md、约束条件），并在会话启动时自动加载。上周犯过错误的智能体本周无法重蹈覆辙，因为教训已存入运行框架在操作前读取的文件中。没有持久化记忆，每次会话都是从零开始；有了它，系统才能持续积累。

实用测试：如果你的 Agent 在第 40 轮还能记住你在第 1 轮设定的约束，说明你的上下文层在正常工作。如果到第 15 轮就忘了，那它就没起作用。

4. 安全护栏（Guardrails）

安全护栏在模型输出到达用户或下游系统之前拦截并验证其是否符合策略。到2026年，这已不再是可选项。科罗拉多州的AI法案已于6月30日生效。欧盟AI法案的高风险条款从8月起适用。SOC 2 审计员现在要求提供对运行时（runtime）输出实施AI控制的证据。

一个常见错误：对所有 Agent 都一视同仁地应用这四类控制措施。面向客户的聊天机器人与拥有数据库写入权限的 Agent 并不需要相同的控制手段。运行框架（Harness）应根据任务的风险等级来调整安全护栏（guardrail）的严格程度，而非在所有环节都施加最大阻力。

四种类型：

行为规范。内容安全、语调、格式规则

数据。PII（个人可识别信息）检测、数据分类。智能体不得将客户数据泄露到日志或 PR 描述中。

工具与操作。权限作用域，针对不可逆操作的草稿提交。

运维方面。Token预算、时间限制、重试（retry）次数上限。智能体不能在一个你预估花费 $5 的任务上烧掉 $200。

5. 可观测性

一个上周还能正常工作的智能体（AI Agent），本周可能毫无征兆地失败，尽管没有任何代码变更。底层模型被静默更新，某个API（API）改变了其响应格式，或者使用量达到了一条未曾测试过的路径。没有可观测性（Observability），你只会在生产环境崩溃时才后知后觉；而有了可观测性，你能在它造成实际损害之前，就检测到性能漂移。

能够trace每个智能体动作并检测行为漂移的组织，才能随着时间推移自信地扩展智能体的自主性。没有追踪记录，每一次范围的扩展都是一场赌博。有了它，这便是一个基于证据的决策。

每次工具调用及其结果。智能体尝试了什么，发生了什么，耗时多久。这条审计轨迹。

每次被接受变更的成本，而非总Token（tokens）数。每次有效产出的成本。若变更接受率低于 50%，则 Harness 所耗多于所省。

漂移检测。将本周的输出分布与上周进行对比。在用户发现之前，先捕获静默的模型性能回退。

6.路由与模型选择

并非每个子任务都需要相同的模型。代码检查（lint check）不需要与架构评审（architecture review）同等的推理能力。没有路由（routing）的 Harness 会将所有任务都交由最昂贵的模型处理，并寄希望于预算能够支撑。而带有路由的 Harness 则会选择能够处理每个子任务的最经济模型，并将昂贵的模型预留给真正需要的环节。

实际的拆分方案是：使用快速、廉价的模型进行分类、格式化和机械化检查。使用强大的模型进行规划、复杂推理以及任何需要判断力的任务。智能体运行框架（Harness）会根据任务类型自动路由，而不是依赖开发者在工作流（workflow）中途记住要切换模型。

7. 反馈与自我改进

静态运行框架在第 50 次运行时与第 1 次运行的方式完全相同。而支持反馈的运行框架则会从每一次拒绝、每一次超时、每一次预算超支中学习，并将这些经验教训写入约束文件，供未来的每次运行自动读取。

这不是模型的微调（fine-tuning）。模型权重并未改变。改变的是围绕模型的系统：规则变得更严格，路由变得更精准，上下文变得更精确。几周后，验证器需要拦截的错误越来越少，因为约束条件本身已经防止了它过去需要标记的错误。

为什么 88% 的智能体在没有它的情况下会失败

这个数字来源于企业部署数据。近九成的AI智能体项目在进入生产环境前就停滞不前，而根本原因几乎从不是“模型不够智能”。问题出在模型周围的基础设施：缺失的层次、跳过的检查、未监控的漂移。以下是真正会导致项目崩溃的地方：

上下文腐烂。长时间会话会丢失约束。第 3 轮的规则，到了第 50 轮就消失了。Agent 被明确告知“绝不修改计费代码”。但到了第 50 轮，上下文摘要已丢弃这条指令。于是，Agent 修改了计费代码。

无验证。Agent 自评其作品，评分总是宽松。一项关于自我评估 Agent 的研究发现，它们94%的时间会批准自己的输出。而一个使用不同指令的独立验证器则将此比例降至61%。这33%的差距，就是那些本应发布出去的缺陷。

工具权限提升。提示词注入触发了 shell 命令。没有权限层能阻止它。在一个有记录的案例中，一个经过精心构造的GitHub issue 描述导致智能体运行了嵌入在 issue 正文中的任意脚本，因为智能体运行框架没有工具级别的权限检查。

静默的模型更新。提供商推送变更。智能体行为悄然漂移。两周无人察觉，因为缺乏可供比对的行为基线。

无状态持久化。每次会话都从零开始。相同的错误每日重复。相同的上下文以全额 Token 成本重新推导。某团队报告称，他们 40% 的 Agent 预算都花在了 Agent 在之前的会话中已经处理过的上下文上。

预算爆炸。循环在失败任务上重试了 40 次。没有任何上限阻止它。账单周一就到。

这里的每一个问题都属于运行框架（Harness）问题，而非模型问题。更换模型后，同样的故障依然会发生。修复运行框架（Harness）后，同一个模型就能开始正常工作。设计运行框架（Harness）最经济的时机，是在第一位真实用户接触智能体（Agent）之前，而不是在第一份事故报告出现之后。

运行框架（Harness）无能为力之处

运行框架无法修正糟糕的任务定义。如果目标模糊不清，即使世界上最好的运行框架也只会稳定地产出错误结果。

安全护栏会失效。权限一旦设定便永不再审，只会带来虚假的安全感。每 30 天必须重新审计。

过度工程化会拖慢速度。每一个审批关卡都会增加延迟（latency）。为银行设计的 Harness 会让黑客松感觉像在报税。请让重量级与风险相匹配。

运行框架本身不是产品。它是基础设施。没有人会购买你的运行框架。他们购买的是智能体产出的成果。

结论

提示词工程（Prompt Engineering）教会我们如何与模型对话。上下文工程（Context Engineering）教会我们该向它们展示什么内容。而 Harness 工程（Harness Engineering）是将它们部署到生产环境的关键环节：谁赋予它们工具，谁来校验它们的工作成果，它们能记住什么，它们可以接触什么，以及是否有人能观测到整个过程。

每家仍在通过“我们应该选哪个模型”这面镜头来评估AI智能体（AI Agent）的企业，问的都是去年的问题。模型是引擎。运行框架（Harness）是汽车。没人会只把引擎裸装出货。

你不需要在第一天就启用全部七层。从工具权限（第1层）和基础验证检查（第2层）开始。当会话开始重复时，再加入记忆功能。当智能体触及客户可见的内容时，再加入安全护栏。当你需要证明系统确实在运作时，再加入可观测性。当 Token 账单变得难以承受时，再加入模型路由。当你希望系统不再犯同样的错误时，再加入反馈机制。

七层架构。工具编排、验证、上下文、安全护栏、可观测性、路由、反馈。跳过任何一层，你就只能产出一个demo。构建所有七层，你将得到一个每次运行都能自我优化的系统。
