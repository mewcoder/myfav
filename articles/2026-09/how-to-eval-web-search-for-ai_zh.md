如何评估用于 AI 的 Web 搜索

作者 @everythingmeta，Parallel 的 MTS

阅读本文，或将其交给您的智能体，以帮助您建立对 Web 搜索 API 的有效评估。

如果您正在使用 Parallel，并希望今天就充分利用我们的 Search API，请阅读我们的最佳实践。

搜索已成为智能体系统不可或缺的一部分。无论您是在构建编码智能体、个人智能体、知识应用，还是其他完全不同的东西——AI 加上搜索会更好！

但一旦开始，您很快就会意识到：选择太多了！提供商、模型、不同的评估技术。如何决定？您应该使用现成的评估吗？用 vibe-coding 做一个？找一个藏在被遗忘角落里的孤独领域专家来生成数据，并让他们标记一个黄金数据集？

答案是……视情况而定！（抱歉。）

本指南的目标是解释为什么搜索评估看起来简单，但实际上并不简单——但也远非不可能——并为您提供一个运行评估的清单，让您和您的子智能体对您在该领域的深厚专业知识印象深刻。

准备好了吗？让我们开始。

搜索、提取，还是任务？

对人类来说，“搜索”是在 Google 中输入关键词或短语。对于使用搜索的智能体来说，世界要丰富得多，也奇怪得多。

人们通常称之为“搜索”的有三种相关任务。它们恰好与我们的产品很好地对应：

搜索（Search）在网络上查找相关信息，供智能体纳入其上下文窗口。不仅有助于找到页面，还能找到其关键信息。
提取（Extract）读取您已有的（或搜索返回的）URL 的内容。也称为“Web Fetch”。
研究或任务 API（Research or Task APIs）接受更大的目标，并为您完成大部分搜索、阅读和基于 LLM 的合成工作。

搜索和提取几乎总是同时使用。LLM 经过专门训练，期望它们可以深入页面。像 Parallel 这样的智能体搜索专门设计为返回密集的片段——与查询相关的页面摘要——从而最大限度地减少对提取的使用。因此，将搜索和提取配对始终是一个好主意，因为模型可以决定是否需要更深入。

尽管大多数开发者首先使用搜索 API，但值得确认您的用例是否更适合使用研究（任务）API。如果任务是“接受这个目标和输出模式，进行搜索和阅读，并返回一个有来源、结构化的答案”——例如丰富公司列表、生成带引用的研究报告——任务 API 可以在一个便捷的端点中完成所有这些。

在配置任何内容之前，先决定您要衡量什么

如果您正在评估搜索，您可能有一个想要解决的问题。也许您正在丰富客户列表、为智能体添加搜索功能，或者查看旧的收益报告。无论您做什么，您可能都在关注这个等式：

智能体框架 + LLM + 搜索 + 提取 = 答案

您能做的最重要的事情是确保您有一组可信的黄金标准标签，并且您端到端地评估整个“框架 + 模型 + 搜索”堆栈。避免只看输出（例如特定的搜索响应）或仅看搜索成本。避免直接将查询传递给搜索 API——您不知道智能体会如何格式化查询或目标，而且您可能会惊讶地发现，智能体在提示方面比人类更擅长。始终评估最终答案。

构建黄金集

最好的数据是您已有的数据。也许您手工辛苦地收集了过去的数据。如果这些数据与您期望使用搜索 API 处理的数据类型匹配，这将是一个很好的评估集。

如果您必须生成合成数据（唉），请先手工生成几个问题，然后再让智能体生成更多。一旦完成，请确保它们在尽可能多的维度上与您预期的生产数据匹配：措辞、领域、答案类型和时效性。

始终审查由 LLM 生成的黄金标签。您在获得结果时会重复此过程，但最好现在就这样做，以免在搜索和推理上花费 token 和金钱。

一些常见的混合内容，只要它们与您的实际工作负载相似：

需要跨来源组合事实的多跳问题。
答案在模型权重中不可用的新鲜问题。
与您实际流量匹配的领域特定问题。

避免过度依赖公共基准。尽管在行业中很流行，但它们反映了特定领域的问题，不太可能与您的问题匹配。此外，一些答案早已在线发布，并已纳入 LLM 和搜索索引的数据集中。如果您使用公共基准（如 BrowseComp、SealQA 等），请确保了解每个基准衡量的是什么，以及它是否适合您的用例。

设置框架

现在您已经准备好运行您的第一次评估了，而且还没到午餐时间。首先：除了搜索工具之外，保持所有内容不变：相同的模型、相同的提示、相同的预算、相同的评判者。将每个提供商作为唯一可用的搜索工具，并让智能体进行多轮交互——智能体经过训练，会搜索、缩小范围，然后再次搜索。不要通过限制它们的轮数来扼杀它们的积极性。相反，考虑限制它们的总搜索预算，以反映您的实际成本考虑。

然后，按照每个提供商的文档建议进行配置。提供商会有不同的方式让他们的搜索发挥优势。

对于 Parallel，我们通常会告诉客户一些常见事项（更多信息请参阅我们的最佳实践）：

目标（Objective）。除了搜索查询之外，提供目标字段可以显著改善搜索结果，提升 10–20%。这允许智能体表达它们正在解决的目标，而不仅仅是它们生成的简短查询。
查询运算符。要求智能体避免发出 site: 和 after:；而是使用 include_domains CLI/API 参数来包含和排除域。
限制。智能体有时喜欢花哨的旋钮，并且会热衷于设置和取消设置高级配置。在大多数情况下，最好告诉您的智能体不要动这些设置。

将搜索模式与搜索模型匹配

除了查询本身，搜索模式是您使用 Parallel 的 Search API 时最重要的杠杆之一。一种思考模式的方式是它们搜索的广度和深度。fast 模式非常适合大多数需要接近前沿质量且成本较低的智能体用例（成本更低 => 更多搜索！），而 advanced 模式则最大化质量。

哪个更好？又是坏消息：视情况而定！

有时答案很明确，比如您有一个特定的产品约束需要解决：也许您的延迟要求需要使用 turbo，或者您的预算要求使用 fast。但在大多数情况下，您应该评估多种模式，并找到最便宜、最快且能达到满意结果的模式。

当然，名称可能具有误导性，所以要看实际结果。

模型也很重要。将廉价的 LLM 与昂贵的搜索配对通常没有意义，反之亦然。所以不要只问：“哪个搜索提供商最好？”而要问：

对于这个任务，在我们能负担的成本和延迟下，哪种模型 × 搜索配置是最好的？

在您实际运行评估之前，您应该考虑如何对答案进行评分。大多数人会使用某种“LLM 作为评判者”的方法，使用高端模型将验证过的真实结果与结果进行比较。有一些常用的技术来衡量这一点：

请记住，召回率意味着“我们找到了正确列表中的多少项”；精确率意味着“我们返回的内容中有多少是正确的？”

信任但核实

使用 LLM 评判器时，切勿盲目信任其结论。确保评判器在返回结果的同时附上其结论的理由。始终至少人工检查 10% 的运行——包括失败和成功的案例。此时你可能会发现一些有趣的发现，并希望将其纳入下一次评判运行中。务必让代理跟踪其已收集的答案，这样你就不必从头重新生成答案，只需重新执行评判步骤即可。

这并不吸引人，但你的代理可能失败的一些原因将是……基本的基础设施问题。以下是我们见过的一些情况：

无搜索调用——代理从未调用工具
提供商错误——超时、5xx、拒绝
检索未命中——查询合理，但结果错误
综合失败——正确结果已在上下文中，但模型仍然回答错误

只有检索未命中和提供商错误是搜索 API 的直接失败。由于评估通常以远高于真实流量的负载运行，许多失败可能反映的是账户限制而非实际能力。

运营成本

请记住，归根结底，重要的是完成任务的端到端成本：搜索支出加上代理在推理搜索返回内容时使用的 LLM 令牌。每次调用更便宜但返回嘈杂、低密度结果的 API 可能总体更昂贵——更多的调用、更多的跳数、每一步上下文中更多的令牌。

因此，请以代理体验的方式衡量成本：

每个已解决任务的成本 =（搜索 + 提取 + 模型令牌费用）/ 已解决任务数

结果长度和跳数作为效率代理指标很有吸引力，但单独使用并不可靠：冗长的结果可以帮助代理提前退出，过度压缩的结果可能迫使额外跳数，而并行工具调用会使跳数低估工作量。跟踪每次运行的总体工具调用次数、端到端延迟和端到端成本——切勿使用替代指标。

解读结果

很少存在单一的“最佳”搜索工具；存在权衡曲面上的点，称为帕累托前沿。在 XY 图上绘制结果——准确性与成本，以及准确性与延迟。你通常是在寻找一个在你最关心的象限中得分“在前沿上”的提供商。

有几种做法能将一个受人信任的基准与一个被忽视或争议的基准区分开来：

置信区间，以及对平局的诚实态度。在约 100 个问题的情况下，一两分的差异通常都在噪声范围内。使用自助法置信区间，并在结果在统计上无法区分时如实报告。一个说“这四个并列”的基准比一个在重叠区间上将其排名为 1–2–3–4 的基准更可信。
标注所有日期。搜索质量和定价不断变化；基准只是一个快照。标注运行日期，并优先考虑使其易于重新运行，而不是维护过时的排行榜。
发布配置。说明模型、每个提供商的模式/层级和参数、结果数量、成本公式和日期。供应商与基准作者之间的大多数争议都归结为未记录的配置。

检查清单
确认你是否需要搜索（相对于提取或研究 API）；如果你的产品用例需要同时进行内容发现和获取（通常如此），则将搜索 + 提取配对使用。
定义具有可验证答案的任务；对代理的最终答案进行评分。
构建约 100 个具有生产代表性、以代理措辞的问题：多跳、新鲜、领域特定。隔离已饱和的基准。
保持代理固定不变；仅更换搜索工具；允许多轮交互。
根据各提供商的文档进行配置；引导代理远离 `site:` 运算符；仅出于产品原因进行限制。
匹配层级；每支运行 3 次以上；报告方差。
使用部署模型进行评估；在同时选择模型和搜索时，评估模型 × 搜索组合。
对照已验证答案进行评判；审计引用；人工检查 10%；将失败分类为四类。
衡量每个已解决任务的成本、总体工具调用次数、每个任务的令牌数以及 p50/p95/p99 延迟。
绘制准确性与成本以及准确性与延迟的前沿图；报告置信区间；平局就说平局；标注日期并发布方法论。

这就是评估智能搜索代理的方法。现在你可以将领域专家从被遗忘的小隔间中释放出来了。
