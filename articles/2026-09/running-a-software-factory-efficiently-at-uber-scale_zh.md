## **引言**

AI工具现已嵌入 Uber 软件开发的每个阶段。超过 70% 的代码合并请求由本地或云端的智能体（agents）完成。工程师们在整个软件开发生命周期中构建了超过 3,600 个智能体（agent） skills，并且每天执行超过 30,000 次agent skill执行。 

在AI工程师 2026 大会上，我们分享了 [我们的愿景](https://youtu.be/17-YSUHo6Lk?si=EbqFAc2UwHX_3wSc) 针对软件工厂以及我们在整个生命周期中构建的构件和托管智能体（Managed Agents）。随着这一愿景的推进，越来越多的会话不再由人类发起，而是由自动化托管智能体处理：代码审查、自我修复 CI 故障、完成带视觉验证的端到端 PR、分类告警、调试新进缺陷，并处理各种需要人工审查/升级的代码维护任务。

如图1所示，从2026年2月至8月，在我们所有员工（工程师与非工程师）中，所有智能体式（agentic）产品的周活跃用户增长了7倍，周智能体请求量增长了9.4倍。与此同时，得益于全面优化，我们的总AI支出自4月以来已相对稳定。

### **优化价格 / Token**

供应商设定 Token 价格。我们决定哪个模型运行哪个工作负载。在我们所有托管智能体的层级中，我们为每个工作负载选择最符合帕累托效率的模型。对我们而言，帕累托效率意味着单次任务完成成本、输出质量和模型可靠性的综合最优。 

#### **基准测试驱动的模型选择**

模型选择分四个步骤进行，对于我们运行的每一个托管智能体都采用相同流程。

-   基于智能体的实际工作构建基准测试。
-   在提供统一接口以服务任何模型（无论是前沿模型还是开放权重模型）的运行框架（harness）上运行 AI 智能体（AI Agent）。 
-   转向帕累托最优（Pareto optimal）方案，并持续跟进。该前沿每几周就会发生变化。

展望未来，我们将持续优化工作负载性能，利用管理智能体汇总的洞见来测试和部署各种模型路由（model routing）策略。

例如，我们使用uReview，它负责所有拉取请求的AI代码审查。我们基于包含已知缺陷的真实拉取请求构建了其基准测试，并将缺陷分为简单、中等和困难三个等级。我们针对这些缺陷评估精确率、召回率和 F1 分数，同时还评估每次审查的成本、延迟（latency）、超时和噪声。如图 5 所示，切换模型在显著降低每次拉取请求成本的同时提升了我们的 F1 分数。在图中，虚线是帕累托前沿。其下方和左侧的所有点，都被更便宜或更好的方案所超越。 

![散点图：比较 10 种模型配置的每条审阅成本与 F1 分数，突出显示帕累托前沿。](./running-a-software-factory-efficiently-at-uber-scale/05.jpg)

图5：我们为uReview测试过的所有配置。

基于我们大型 monorepo 中数千个真实世界的 PR，我们内部也构建了一个 Uber SWE 基准，它针对不同任务类型运行前沿和开放权重模型。我们使用它来为所有受 SDLC 管理的 Agent 进行模型选型提供依据。

#### **默认模型选择**

在交互界面中，Token 单位成本保持固定；但你可以通过策略性方式管理跨模型的 Token 分配。主要由两个默认设置控制这种分配：初始会话模型和子 Agent（subagent）模型。

子 Agent（Subagent）的默认设置已被证明是最具影响力的杠杆，且其重要性持续增长。随着最新模型的能力使得更有效的子 Agent（subagents）编排成为可能，启动多智能体（multi-agent）的会话比例稳步上升。由于子 Agent 执行的是定义明确、输入具体且通常不需要前沿推理能力的任务，我们将其默认为更弱、更具成本效益的模型，同时仍允许手动覆盖。主模型负责任务拆解（task decomposition）和评测（evaluation），而子 Agent 则执行实际工作。

### **优化每次请求的 Token 使用量**

每一轮对话都会重新发送完整的对话历史、项目上下文和工具结果。任何能减少单次请求负载的优化，其效果都会在整个会话中累积放大。

#### **默认值**

所有交互式 Harness 均使用统一的封装层来管理安装、配置、身份验证和成本可见性。两种标准化的默认配置直接减少了每个请求的 Token 用量：

-   **自动压缩在 400k Token 时触发，即使对于拥有 1M 上下文窗口（context window）的模型也是如此：** 这个阈值在模型性能、缓存突发和重复输入 Token 成本之间取得了平衡。我们的测量显示，整个集群的每请求输入 Token 数量有显著减少。
-   **推理努力默认设为中等**：在主要模型上，输出 Token（包括内部推理 Token）的计费费率是输入 Token 的倍数；此项策略调整直接降低了最高成本类别的支出。对于一大类任务而言，中等推理在成本与质量之间取得了良好平衡。

#### **提示词缓存策略（Prompt Caching Strategy）**

我们的提示词缓存策略由提供商提示词缓存读写的经济性驱动。由于每轮对话都会重新传输完整的对话历史，缓存前置上下文可以避免重复支付全部费用，将后续读取成本降至标准输入 Token 费率的 0.1 倍。然而，写入溢价有所不同：5 分钟缓存条目成本为 1.25 倍，而 1 小时条目成本为 2 倍。因此，选择最佳的 TTL（生存时间）取决于对话轮次之间的间隔时长。可用的 TTL 选项包括 Anthropic® 提供的 5 分钟和 1 小时，以及OpenAI® 提供的 30 分钟。

![对比主线程和子 Agent（Subagent）场景下 5 分钟与 1 小时 TTL 缓存的成本，展示成本节省情况。](./running-a-software-factory-efficiently-at-uber-scale/06.jpg)

图 6：在两种 TTL 持续时间下，5 轮对话的比较。

由于工程师常将交互式会话空闲超过5分钟，我们已将默认的5分钟生存时间（TTL）调整为1小时窗口期。此前频繁的空闲间隙会导致前缀缓存失效，迫使系统进行代价高昂的全价上下文重建。相比之下，子 Agent 保留5分钟缓存生存时间，因为其执行焦点仅限于单一短期任务。

#### **通过 Shell 执行MCP工具**

在 Uber，所有MCP (模型上下文协议（Model Context Protocol）) 交互都通过一个统一的网关进行路由。这单个入口点涵盖了超过 1,000 个内部和第三方 SaaS MCP的MCP服务器，从而实现了集中的认证和策略执行。

然而，标准的MCP会将所有工具 schema 直接加载到每个会话中，无论工程师在该会话中是否会实际调用它们。例如，当安装了超过 100 个工具时，这种预加载会在初始 prompt 中增加大约 50K-70K token 的模式（schema）开销，而这个初始 prompt 会在每次 context 轮转时被重新发送。

![Token 用量（token usage）的比较：安装每个服务器大约消耗 50,000-70,000 个 Token，而工具搜索加上CLI几乎不消耗 Token。](./running-a-software-factory-efficiently-at-uber-scale/07.jpg)

图 7：智能体（Agent）在会话开始时已携带的内容，在 3 种不同方式下达到相同工具时。

为了解决这种上下文膨胀问题，我们引入了两种互补的优化机制：

-   **CLI工具解析**：通过允许模型执行 shell 命令，取代了直接的MCP集成。该CLI在调用时动态解析并调用所需工具，从而将 Uber MCP schema 从会话上下文中移除。我们内部MCP网关中所有超过 1000 个的MCP工具，都以CLI命令的形式呈现。
-   **工具搜索**：通过允许模型搜索工具目录并按需加载所需工具，实现数千种工具的可扩展性。这种方法减轻了上下文膨胀，通常减少了工具定义的 Token 用量，并在可用工具库扩展时仍保持高选择准确度，防止了因大型工具集而带来的性能下降。

#### **Code-Mode**

当工具将函数作为 shell 命令直接调用时，模型可以在单个脚本中批量执行多个操作。这种批量处理对于交互频繁的工具协议尤其有利。在标准的MCP工作流下，每个操作都需要模型进行一轮单独交互：发出请求、将原始响应加载到上下文窗口，并按顺序处理结果。例如，执行单个 SQL 查询需要提交请求、轮询状态 2 到 5 次，然后获取输出。代码模式将这整个流程简化为一个自动化的Python循环，将中间轮询过程排除在模型的活动上下文之外。如左侧图 8 所示，模型参与到轮询循环中，每次响应都会进入其上下文。而在右侧，循环在子进程中运行，只有摘要结果返回。

#### **SaaS MCPs**

管理第三方软件的难度远高于管理我们的内部服务器。厂商设计MCP服务器时，会暴露产品的全部能力，因为他们无法预测特定客户的具体使用方式。例如，某工作区套件将 49 个工具捆绑在一个服务器中，需要约 22K 个 token 的 schema；而消息传递和项目跟踪厂商分别提供 34 和 46 个工具。加载两到三个厂商服务器，就会让智能体携带的 schema 开销，比用户输入提示词之前正在编辑的文件本身还要多。

为了解决这个问题，我们通过MCP网关路由 SaaS MCP服务器，使用了与我们内部 MCP 相同的机制。我们还将所有这些 MCP 作为 CLI 暴露出来，以便任何 Agentic 界面都可以调用。此外，我们在代码模式插件中为每个服务器编写了专用的 Agent Skill，以封装常见的工作流。这使得跨多个 SaaS 供应商的高效 Agentic 工作流成为可能。

**优化请求轮次（Requests / Turn）**

一个缺乏上下文的智能体会缓慢而高昂地失败，不断向已扩展的上下文窗口发送请求以搜索下一个位置。预先提供更丰富的信息，仍然是降低这种搜索开销的最有效手段。

#### **上下文工程（Context Engineering）**

在 Uber 庞大的代码库和数据生态系统中——包含数亿行代码和数千张表——智能体大部分时间都花在定位信息上，而非生成代码。为解决此问题，我们构建了AI上下文图（AI Context Graph）：这是一个统一的网络，包含 2400 万个节点（nodes）和 8000 万个边（edges），涵盖 86 种节点类型和 117 种边（edge）类型。它集成了来自 30 多个内部系统的数据，包括服务、工程团队、事件日志、拉取请求、架构设计文档、部署、数据集以及历史表使用查询，并允许任何智能体以自然语言对其进行查询。

![使用图进行查询耗时 38 秒且结果正确；未使用图进行查询耗时 20 分 09 秒且结果错误。](./running-a-software-factory-efficiently-at-uber-scale/10.jpg)

图 10：对比同一提示词提交给相同模型时，有无图结构化（Graph Grounding）的执行路径差异。

有数据表权限的智能体查询了历史使用记录，识别出超过 50 名分析师使用的特定表，并在 38 秒内给出了答案。相反，无数据表权限的智能体无法访问该表；它花费 20 分钟检查服务代码，启动 2 个子 Agent，遇到 3 次错误，最终错误地得出数据集无法查询的结论。

**可见性与支出层级**

为避免强加严格限额，我们实现了实时支出追踪与自动提醒机制：

-   **状态栏实时计数器。** 运行中的会话始终在终端中显示当前成本。 
-   **Harness 池。** 为所有交互式 Harness 提供一个共享层级，而非按工具分配预算。托管 Agent 拥有独立的层级。
-   **Slack 提醒通知。** 在达到预期支出 50%/80%/100% 时发送警报，以便工程师有时间进行规划。
-   **简洁的审批流程。** 经理对层级升级的审批签字，并可快速同步。
-   **成本检查技能与技巧。** 一项用于按需成本分解和实时状态行指导的仪表盘技能。

这些机制使工程师能够独立评估任务的投资回报率（ROI），同时规避费用失控的风险。

#### **会话分析仪表盘**

虽然状态栏突出了会话的总开销，但缺乏对成本驱动因素或可操作的效率优化步骤的可见性。通用指导提供了高层次的原则，但无法评估个体开发者的工作流。会话分析仪表板通过直接检查会话工件来弥合这一鸿沟。

它直接内建于运行时（runtime）中，无需任何设置或主动启用。执行 _cost dashboard_ Agent Skill 会分析该用户在所有使用的 Harness 中，跨越本地和远程云沙箱的所有会话轨迹。它不会生成一个聚合指标，而是会标记出 16 种不同的反模式，并为每种反模式配对其财务影响以及针对性的修复建议。部分类别包括：

-   **次优模型路由：** 在 Opus 上执行 Sonnet 本可轻松完成的简单多轮会话。
-   **上下文窗口膨胀：** 大型MCP负载（例如 40KB 的响应）持续存在于上下文中，并在后续轮次中引发重复计费。
-   **缓存过期效率低下：** 在长时间中断后恢复会话时，过期的提示词缓存会强制进行全价前缀重建。
-   **提示词初始化开销：** 在提供任何用户输入之前，预先加载 100,000 个 Token 的系统指令和工具定义。

**下一步是什么？**

当前进行中的计划包括：

-   **扩大托管智能体（Managed Agents）的规模：**对于每个新增的智能体，我们都遵循一致的路线图：确定目标成果指标、构建评测基准，并识别一个帕累托最优模型。这种系统性方法旨在提升软件开发生命周期（SDLC）的每个阶段，使其更接近工厂成熟度模型的更高水平。
-   **动态模型路由：** 我们正在扩展涵盖多种编程语言、代码仓库和智能体模式的基准测试覆盖面。由于模型能力差异巨大，有效的模型路由在很大程度上依赖于全面的评估。
-   **深化上下文图集成：** 我们正在为更广泛的自治智能体（Autonomous Agents）解锁图查询能力。
-   **将会话分析演进为实时开发者指导：** 通过将反模式检测从定期批量方式转变为持续的trace监控，我们旨在将个性化、实时的效率建议直接提供给工程师。
-   **持续技能改进（Continuous Skill Improvement）**：我们正在开发一种自动化方式，用于记录 Agent Skill 执行中的小问题（papercuts），并基于收集到的 Trace 自动生成技能更新。

## **结论**

管理和遏制不断上涨的AI编码费用，也是一个可解决的工程挑战。通过消除浪费的、零价值的 Token 消耗，而非仅仅依赖更低的单价或降级工具链，我们实现了用量 7 倍的增长，同时将所有指标的单位成本降至更低，并提升/维持了输出质量。

核心战略转变在于从交互式开发者工作流迈向全托管智能体。将软件开发生命周期（SDLC）工作负载迁移至托管环境，可实现对模型路由、执行 Harness 及运维成本的完全掌控。相较于为数千名工程师各自优化独立终端会话，优化一个由专用托管智能体组成的集群——每个智能体都配有专属评测基准与帕累托高效模型——在本质上更具成本效益和可扩展性。
