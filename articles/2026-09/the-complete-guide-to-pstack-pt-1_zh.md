pstack 完全指南 第 1 部分

在这个系列文章中，我将展示我如何使用 pstack——我个人的一套严谨工程技能。它让我能够以高置信度每月向生产环境交付 2,000 个 PR。

就我个人而言，我从未过多关注我提交了多少行代码或多少个 PR。在智能体出现之前，没人关心这些，而且理所当然，因为原始生产力并不总是等同于质量或用户可见的成果。这只是一个虚荣指标。

但我在构建 pstack 的过程中发现，数量确实很重要，尤其是当你能够借助智能体保持甚至提升产品质量时。例如，大约 2 个月前我开始参与 Grok @Bot 的工作，当时它还处于早期阶段，代码库很新但开始增长。尽管团队在扩大，现在每天有数百个 PR 合入 Grok @Bot 代码库，pstack 让我能够通过持续监控代码、重构、添加新的 lint 和检查，以及开发功能，为所有人保持代码的高质量。

https://x.com/i/web/status/2090546476464451907

作为 Grok @Bot 的园丁和维护者，只有通过 pstack 我才能做到这一点。我们在构建原型后的早期势头非常强劲，许多人加入了团队。我面临一个关键的机会窗口：在代码库被构建和扩展且不停机的情况下，将其重构为一个基础扎实的系统。一个高质量的代码库，无论有多少工程师（更重要的是，非工程师）参与贡献，都能扩展。所有这些工作都要求我在 Grok Bot 构建过程中重构和改进其基础，而只有当基础能够跟上贡献数量时，你才能做到这一点。

Grok Bot 是市场上最高效、性能最好的 AI 桌面应用之一

证据就在 Grok @Bot 本身。在接下来的几周里，我将告诉你使用 pstack 构建和维护高质量应用所需的一切。

第 1 部分——验证就是一切

你的工具箱中最关键的技能是高质量的验证技能。这项技能如此重要，以至于我把它视为关键基础设施，而不仅仅是“一项”技能。一个好的验证技能会放大你整个团队的产出，包括非工程师。如果做得好，你团队的产出将提升 100 到 1000 倍。

如果你不熟悉这个术语，验证意味着智能体可以验证自己的工作。它可以持续进行直到成功完成任务，因为它现在可以闭环，而无需你成为瓶颈。如果你有兴趣了解更多我是如何为 Cursor 创建第一个验证技能的故事，请查看我之前的文章《你可以信赖的循环》。

让我们一起构建一个验证技能

首先，安装 pstack，然后运行 /create-verification-skill。我还建议你将 Dr Eggbot 添加到你的团队中，这是我的机器人，可以帮助你创建高质量的机器人。Dr Eggbot 随 pstack 一起发布。它会教编码机器人如何使用它，并且它也可以用同样的严谨性创建非编码机器人。

你可以让 Dr Eggbot 为你创建一个工程师机器人，然后让该机器人运行 /create-verification-skill，并设置每日例程来运行 /maintain-verification-skill。

喜欢 Dr Eggbot

在运行的同时，让我们来看看这个技能做什么，以及它如何为你创建一个高质量的验证技能。

我将我们用于构建 Grok @Bot 和 Cursor 的所有验证技能提炼到这个技能中，作为一种元技能。它教会你的智能体如何为你的应用创建高质量的验证技能。

现在，技术栈的选择很重要。例如，如果你在 Electron 或 Web 上构建应用，你可以利用 JS 生态系统中丰富的调试工具。例如，Chrome DevTools 协议（CDP）允许你使用浏览器开发者工具中可用的相同工具。或者，如果你在构建 iOS 应用，可以使用模拟器。

理想情况下，你需要能够与你的应用交互、调试它、获取性能跟踪，以及任何你手动开发应用时通常会使用的调试和开发工具。如果你没有丰富的运行时可用，你可能需要让智能体为你创建工具（例如使用 lldb，或在开发环境中作为 sidecar 运行的自定义包），或者直接使用你现有的工具。

我个人认为，智能体验证如此重要，以至于我会认真建议构建你自己的丰富调试工具，甚至选择不同的技术栈，以便在软件开发中获得不公平的优势和极高的生产力。正如我之前提到的，让智能体能够验证自己的工作，可以解锁组织中每个人的贡献能力，并验证他们的更改确实有效。你的技术栈越难调试和控制，就越难有效地使用智能体。

使其可复现

在 pstack 中，我们有一个原则叫“构建杠杆”。在创建技能的背景下，这意味着我们更倾向于给智能体工具，而不仅仅是 Markdown。对于验证技能，这意味着创建一个小的 CLI，将应用的交互和调试脚本化到一个小的、智能体友好的实用工具中。这意味着智能体在尝试完成任务时消耗更少的 token（运行 CLI 命令，而不是编写一次性脚本来点击某些东西），并使你的验证技能更具可复现性和可测试性。

以下是一个假设的 CLI 示例，你的智能体可能为 Electron 应用创建：

shell
# 健康检查
node .cursor/skills/verify-atlas/control-atlas.mjs doctor

# 打开空白线程并发送
node .cursor/skills/verify-atlas/control-atlas.mjs new-session
node .cursor/skills/verify-atlas/control-atlas.mjs send "列出此项目中的开放任务"

# 键盘路径
node .cursor/skills/verify-atlas/control-atlas.mjs press "Meta+KeyN"

# 实时 UI 的无障碍快照
node .cursor/skills/verify-atlas/control-atlas.mjs snapshot

# 截图作为证据
node .cursor/skills/verify-atlas/control-atlas.mjs screenshot /tmp/atlas-proof.png

# 等待流式传输/布局稳定
node .cursor/skills/verify-atlas/control-atlas.mjs wait-settle

# 为会话切换功能标志
node .cursor/skills/verify-atlas/control-atlas.mjs feature-flag rooms_v2 on

现在，所有智能体都可以使用这个 CLI 快速导航和调试你的应用。你还需要开始考虑构建应用的开发体验：

- 种子开发数据库
- 如何处理认证、测试用户、对测试/暂存环境的 API 调用
- 以一致的方式安装和启动你的开发环境

这些可能都是你自己写代码时需要考虑的事情。所以把它看作你的智能体在你的应用上进行开发工作的主要工具。保持它的良好维护和测试！

你可能还想考虑的其他示例命令：

markdown
- **检查：** `info`, `snapshot`, `screenshot`, `components`
- **导航：** `home`, `new-session`, `select-project`, `select-runtime`, `scroll`
- **交互：** `send`, `click`, `click-xy`, `aria-click`, `type`, `press`, `eval`, `upload-image`, `add-context`, `feature-flag`
- **性能：** `trace`, `profile`, `record`, `perf-metrics`, `wait-settle`
- **流式传输：** `console`, `network-log`, `network-summary`
- **健康与清理：** `doctor`, `cleanup`, `watch --restart`

一旦你有了这个基本设置，你应该会开始看到智能体的巨大改进。它们应该能够轻松地导航和调试你的应用。

我建议在推进更高级的功能之前，先花时间把 CLI 打磨得完善且无错误。你还需要考虑（或让代理帮你考虑）设计一个对代理友好的 CLI。网上有很多资源可以供你的代理参考，但我比较看重的关键特性包括：

- API 易于组合——可以参考 John Ousterhout 的“深模块”哲学
- 任何可能产生破坏性副作用的命令都应提供 `--dry-run` 选项
- 利用子命令逐步展示功能，而不是一次性全部暴露
- 错误信息应非常详细，并告诉代理应该怎么做
- 提供丰富的 `--help` 文本
- 输出采用机器可读的格式（如 JSON）

**用云代理实现并行加速，而不是依赖 worktree**

当你的验证技能成功落地几个 PR 之后，你可能会开始思考能否进一步并行化。例如，如果代理现在能根据你的提示基本独立地将其推进到可合并状态，那是不是意味着你可以同时运行更多代理？

你的第一反应可能是添加 worktree 支持，也就是让代理用 git 创建仓库的跟踪副本，在主检出之外隔离地进行修改。理论上，这可以让你同时运行多个代理，而不会让彼此的修改互相冲突。

我建议不要这么做。首先，它会占用你机器上大量的存储空间和资源。根据仓库大小和机器性能，你可能勉强能并行运行 10 个带 worktree 的代理。但还有更好的方案！

Cursor 的云代理是在云端、Cursor 的基础设施上运行的代理。这些代理拥有真实的计算机环境，可以安装依赖、运行应用、录制视频和截图，并能像真实用户一样与应用交互。如果你在之前的步骤中投入足够精力优化了开发体验，那么配置云代理应该不是什么大工程。首次配置云环境时，我们会派一个代理帮你完成设置并确保一切正常运行。首次构建完成后，我们会生成一个快照，这样后续的云代理运行都能快速启动。

我强烈建议花时间配置云代理，因为它能极大地提升并行生产力。在后续的文章中，我会展示如何在云端并行运行数百个子代理！但现在，先把你的环境配置好，让它达到一个让你对在云端运行所有代理有信心的状态。

**用功能地图保持代理的智能**

随着应用变得越来越复杂，代理需要更多指导才能找到功能并与之交互。为此，我设计了一个叫“功能地图”的方案。顾名思义，它是一份易于搜索的地图，列出了应用中所有可用的功能、功能的作用以及从用户角度如何访问这些功能。

下面是我为一个虚构应用 Atlas 准备的功能地图示例。它只是几个 markdown 文件，在验证技能的 SKILL.md 中被引用。

你可以把这个文件放在任何位置，但在 `/create-verification-skill` 中，我们会自动创建一个 `references/features` 目录，旁边还有一个 `README.md`。这个 README 就是地图本身：对所有主要功能的高层概览，并附有指向具体细节的链接。一个功能示例如下：

```markdown
# 偏好设置

全屏偏好设置浮层及其标签页集合。

## 子功能

- settings-overlay：从齿轮图标或 Cmd/Ctrl+, 打开的全屏浮层
- settings-nav：左侧标签页导航（通用、外观、模型、套餐与用量……）
- settings-search：浮层内搜索（设置打开时按 Cmd/Ctrl+K）
- theme-picker：外观页中的快速主题控制

## 如何访问（用户视角）

点击账户头像旁边的齿轮图标，或按 Cmd/Ctrl+,。从左侧导航选择一个标签页。在偏好设置搜索框中输入以跳转。按 Escape 或点击关闭控件即可退出。

## 用 control-atlas 驱动

bash
node .cursor/skills/verify-atlas/control-atlas.mjs press "Meta+Comma"
node .cursor/skills/verify-atlas/control-atlas.mjs snapshot
node .cursor/skills/verify-atlas/control-atlas.mjs press "Escape"
```

- 浮层根节点：在无障碍树中查找名为“偏好设置”的对话框/区域。
- 标签页：按可见名称点击。某些账户状态下可能没有“套餐与用量”标签页。
- 设置打开时，Cmd/Ctrl+K 是偏好设置搜索，而不是全局命令面板（参见 `multi-surface-journeys.md`）。

## 注意事项

- 在测试套件中途关闭设置可能会让焦点丢失。`new-session` 或 `home` 可以恢复。
- 某些标签页受权限控制。跳过时需注明明确的账户原因。

不用担心自己手写这些！当你运行 `/create-verification-skill` 时，你的代理会自动遍历你的应用，整理所有内容并为你创建这些参考文档。

功能地图与 CLI 结合，是 pstack 验证技能如此出色的主要原因之一。代理现在对每个功能及其访问方式都有了上下文，节省了上下文窗口中宝贵的 token，并精确地告诉它功能是什么以及如何到达。

你可以把功能地图看作一种“物化记忆”。如果你使用代理已经有一段时间，可能对“记忆”的概念很熟悉——通常这些记忆可能以简单的 markdown 文件（如 Obsidian 库）存储，甚至用更复杂的方案如向量数据库。就我个人而言，我认为你的代码库才是终极的记忆形式。代码是你和团队所做决策的投影，是事情如何发生、系统如何运作的真相来源。功能地图只是它的一种更紧凑的形式，旨在节省 token。而且因为它只是技能中的 markdown 文件，所有为代码库做贡献的人都能从这份共享记忆中受益。

这意味着维护验证技能非常重要。我建议至少每天运行一次 `/maintain-verification-skill`，确保你的代理始终掌握控制应用的最新细节。你可能还会发现，随着你更多使用验证技能，代理在开发应用时会自动更新这些文档。`/maintain-verification-skill` 会捕捉到遗漏的部分。

**如何使用你的验证技能**

供参考，这里有一个为虚构应用创建的验证技能示例：https://github.com/poteto/verification-skill-example. 提醒一下，运行 `/create-verification-skill` 可以创建一个，其中包含基本的 CLI 和功能地图。

以下是我通常如何在 pstack 中使用它的。

首先，当然是用 `/poteto-mode` 作为提示的开头。如果你通过 Cursor 使用 pstack，在自动补全 `/poteto-mode` 时，可以按 Opt + Enter 而不是只按 Enter——这会把技能添加为自定义模式，固定该技能，让你的代理在每一轮新对话中都会收到使用该技能的提醒。

输入 `/poteto-mode` 并按 Opt + Enter 将其固定为自定义模式

在 Grok @Bot 中，安装插件，然后输入 `/poteto-mode`。

你也可以在 Grok Bot 中使用 pstack！

**示例：构建新功能**

在构建新功能时，我通常会结合使用验证技能和 `/poteto-mode`，让代理验证自己的工作。例如，我可能会这样提示：

`/poteto-mode` 构建 <description of feature, any useful context>。使用 `/control-app` 验证你的更改，并给我看视频和截图作为证明

其中 `/control-app` 是 `/create-verification-skill` 的产物。在 Grok @Bot 中，我会这样提示：

生成一个云代理，使用 `/poteto-mode` 构建 <description of feature, any useful context>。使用 `/control-app` 验证你的更改，并给我看视频和截图作为证明

这里的小区别在于，在 Grok @Bot 中，你指示你的机器人去生成一个云代理，而不是让它自己完成工作。我倾向于这样做的首要原因是，它能释放你的机器人去处理其他事务，并保持其上下文窗口的整洁。从这个意义上说，我更多地将我的机器人视为协调者，负责管理和监督云代理。云代理还意味着你可以利用 Cursor 中提供的全系列模型，这些模型拥有各自独立的机器，因此你的机器人电脑可以腾出来处理其他事情。

示例：性能优化工作

生成一个云代理，使用 /poteto-mode 来改善我们应用的初始加载时间。首先使用 /control-app 对现状进行追踪，并识别改进机会。然后进行有针对性的修复，并使用 /control-app 配合 /swarm 来确认改进效果

/swarm 是与你的验证技能结合使用的最佳技能之一。它可以派生出任意数量的云代理来运行你的验证技能，这样你就可以做诸如以足够大的样本量确认性能改进，或者对你的应用进行模糊测试以确保你没有破坏或回归任何功能。

示例：自动复现用户报告

当你对自己的验证技能感到满意时，你可以将它们放入 Grok @Bot 的例程或 Cursor 的自动化中。例程和自动化允许你按计划运行，或在任何事件发生时触发。

例如，如果你将用户反馈接入 Slack，和/或拥有自己的内部反馈渠道，你可以让你的机器人监听每一份报告，并自动尝试用云代理复现它们。如果你的验证技能和功能地图足够好，你甚至可能决定同时自动修复问题。

我之前说验证是你工具箱中最重要的技能之一，这是有原因的。它为你在此基础上构建新技能和例程提供了基础。最重要的是，你团队中的每个人都能从中受益。

投资于你的验证技能

一旦你创建了你的验证技能，请通过 /maintain-verification-skill 保持其敏锐度。持续改进 CLI，并像投资关键基础设施一样投资这项技能。你甚至可能想要为其设置值班轮换——这就是它对于解锁团队 100-1000 倍生产力的重要性。

这项技能是我们在 pstack 指南中将涵盖的许多其他技能的基础，并且能与所有这些技能完美地组合使用。
